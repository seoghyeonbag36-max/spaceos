# eli5-spaceos — SpaceOS를 그림으로 설명하는 슬라이드

`/eli5` 는 주제 하나를 설명한다. 이건 **SpaceOS 전체를 슬라이드 한 벌로** 낸다 —
PPT 에 넣거나 그대로 띄워서 발표하는 것이 목적이다.

**범위 인수**: `$ARGUMENTS`
- 비었거나 `전체` → 아래 11장 기본 구성
- `page` · `platform` · `posting` · `program` → 그 트랙만 5~6장으로 깊게
- 그 밖의 문장(예: `왜 3D를 버렸나`) → 그 주제만 3~5장

---

## 1) 숫자는 문서가 아니라 산출물에서 읽는다

발표 자료에 틀린 숫자가 한 번 나가면 되돌릴 수 없다. **쓰기 전에 반드시 실행한다.**

```
python scripts/pppp_status.py          # 거점 수 · 트랙 진행률 · 게이트별 근거
python scripts/chain_status.py --all   # 거점 축(어느 거점이 어디까지 왔나)
```

- 슬라이드에 적는 모든 수치는 **그 자리에서 이 스크립트가 찍은 값**이다.
- `docs/*.md` 와 `CLAUDE.md` 는 **왜 그렇게 만들었는지**를 읽는 곳이지 숫자를 베끼는 곳이 아니다.
  이 저장소의 주된 실패 양식이 "선언이 조용히 낡는 것"이다 — 거점 수가 문서마다
  13 · 22 · 54 · 73 으로 남아 있다. 그중 **73 은 서빙 거점 수가 아니다**(보류 도시 포함).
- 확인 못 한 값은 **슬라이드에 안 적는다.** 비워 두는 편이 틀리게 적는 것보다 낫다.
- 트랙 진행률 100% 는 "게이트 배선이 끝났다"는 뜻이지 "제품이 끝났다"는 뜻이 아니다.
  발표에서 그렇게 읽히면 안 되므로, 진행률 슬라이드에는 **그 숫자 밖에 있는 것**
  (B2B 파일럿·보류 도시·관측 전용 게이트)을 반드시 같이 적는다.

배경 읽기(주장 아니라 근거용): `docs/feature-page.md` · `feature-platform.md` ·
`feature-posting.md` · `feature-program.md` 의 `0. 구현 현황`, 그리고 `docs/blueprint/`.

## 2) 기본 구성 — 11장

| # | 슬라이드 | 한 장에 담는 것 |
|---|---|---|
| 00 | 표지 | 제품명 · 한 줄 정의 · 날짜 · 대상 |
| 01 | 한 문장 | "비어 있는 가게 자리를, 누가 들어오면 되는지까지 알려준다" |
| 02 | 지금은 이렇게 한다 | 감 · 발품 · 중개 — **문제를 그림으로**(데이터 없음) |
| 03 | PPPP 한 장 | Platform · Page · Posting · Program 네 칸 + 흐르는 화살표. 4P 를 **1:1** 로 붙인다 — `PLACE ▶ PLATFORM` · `PRODUCT ▶ PAGE` · `PRICE ▶ POSTING` · `PROMOTION ▶ PROGRAM` |
| 04 | Page (Product ▶ Page) | 이 플랫폼에 **어떤 page** 를 놓을 자리인가 — 히트맵 + 층 스택 + 네이버 거리뷰 |
| 05 | Platform (Place ▶ Platform) | 이 상권은 **어떤 플랫폼**인가 — 옆가게끼리 끌어주는 힘(GNN) |
| 06 | Posting (Price ▶ Posting) | **어느 가격대의 page** 를 올리나 — 3단 폴백(좋은 데이터 없으면 물러난다) |
| 07 | Program (Promotion ▶ Program) | 올린 다음 **어떤 홍보 program 을 도나** — 온라인/오프라인 두 갈래 |

⚠ **4P 대응은 2026-09-05 에 1:1 로 재정의됐다.** 종전 슬라이드는 Page 에 `PRODUCT / PRICE`,
Posting·Program 에 `PROMOTION` 을 나란히 적었다 — 그 라벨을 다시 쓰지 말 것.
정본은 `CLAUDE.md` §PPPP Framework.
| 08 | 데이터가 어디서 오나 | Bronze → Silver → Gold 3층 파이프 |
| 09 | 지금 어디까지 됐나 | §1 스크립트 값 + "이 숫자 밖에 있는 것" |
| 10 | **이번 미팅에서 필요한 것** | 디자이너에게 부탁할 화면·결정 3~5개 |

마지막 장이 미팅의 목적이다. 설명만 하고 끝나면 미팅이 안 굴러간다 —
**무엇을 정하고 나올 것인지**를 적는다. 호출할 때 미팅 목적을 인수로 주면 그걸 쓰고,
없으면 만들기 전에 한 번 묻는다.

## 3) 그리는 규칙 (ELI5)

- **슬라이드 1장 = 개념 1개.** 두 개면 두 장으로 쪼갠다.
- 글자는 제목 1줄(14자 이내) + 부제 1줄 + 라벨 몇 개. **본문 문단 금지.**
- 설명은 문장이 아니라 **그림**이 한다. 그림이 없으면 그 장은 아직 안 된 것이다.
- 비유를 쓰면 **매핑을 한 줄로 밝힌다** — "옆가게 인맥 = GNN(그래프 신경망)".
- 전문용어는 처음 나올 때 괄호로 쉬운 말을 붙인다. 두 번째부터는 그냥 쓴다.
- 모르는 것을 아는 척하지 않는다. 한계는 작은 회색 각주로 **남긴다**
  (예: "유동·밀도는 집계구 단위 — 격자 실측이 아니다").

## 4) HTML 규격 — PPT 에 들어가는 것이 목적

- 슬라이드 = `<section class="slide">`, **1920×1080 고정**(`width:1920px; height:1080px; overflow:hidden`).
- 인쇄 규칙을 넣어 브라우저 인쇄→PDF→PPT 삽입이 되게 한다:
  `@media print { @page { size:1920px 1080px; margin:0 } .slide { break-after:page } }`
- **외부 요청 0.** 웹폰트 CDN · 아이콘 라이브러리 · 이미지 URL 전부 금지 —
  미팅장 와이파이에 자료를 걸지 않는다. 그림은 **인라인 SVG**, 이미지는 data URI.
- 폰트: `"Pretendard","Malgun Gothic","Segoe UI",sans-serif` (설치 안 돼 있어도 깨지지 않게).
- 색은 `design/tokens/tokens.json` 값만 — brand `#0EA5B7`, ink `#1C2533`,
  공실 5단 `#22B07D→#E03E36`. **네이버 green `#03C75A` 은 네이버 연동을 말하는 자리에만.**
- 톤은 기존 `docs/blueprint/SpaceOS_Blueprint.html` 과 같은 계열
  (딥네이비 `#0A1826` + teal). 같은 미팅에서 두 자료가 다른 브랜드로 보이면 안 된다.
- 키보드 넘김(←/→)과 `?scroll` 로 전체 훑기를 넣어 두면 발표와 검토 둘 다 된다.

## 5) 출력 위치

```
docs/eli5/SpaceOS_ELI5_<범위>_<YYYY-MM-DD>.html   # 원본 (이걸 띄워서 발표해도 된다)
docs/eli5/SpaceOS_ELI5_<범위>_<YYYY-MM-DD>-NN.png # 슬라이드별 PNG (PPT 에 붙이는 것)
```

PPT 삽입은 **PNG 붙여넣기**가 가장 안전하다. 인쇄→PDF 는 폰트·여백이 브라우저마다 다르다.

---

## 6) 내기 전에 확인한다

1. playwright(또는 chrome-devtools) MCP 로 **1920×1080 뷰포트**에 띄워 슬라이드마다 스크린샷.
   → 잘린 글자 · 넘친 박스 · 겹친 라벨을 눈으로 본다. 안 보고 내지 않는다.
2. 네트워크 요청 목록이 **비었는지** 확인(외부 의존 0).
3. 슬라이드의 숫자를 §1 스크립트 출력과 **한 줄씩 대조**한다.
4. 다 되면 파일 경로와 "무엇을 정하고 나와야 하는지"를 같이 보고한다.

## 7) 링크로 공유해야 하면

Artifact 로 게시하면 링크가 나온다(발표 전 원격 검토·모바일 확인용).
게시하더라도 **PPT 에 넣는 것은 로컬 PNG** 다 — 미팅장 네트워크를 신뢰하지 않는다.
