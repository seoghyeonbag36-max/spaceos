## 0-V. 대상 재정의 — 검증하려는 창업자 (2026-09-17)

### 무엇이 바뀌었나

| | 종전 (07-18 → 08-16 → 08-29) | 지금 |
|---|---|---|
| 대상 | 상권 안 **영업 중인 가게**(08-16 에 '공실에 입점할 기업'이 더해졌지만 입력은 가게 전제였다) | **예비창업자** · 자기 아이템이 통하는 상권을 찾아 **팝업스토어·가오픈·MVP 로 검증하려는 기창업자** |
| 묻는 것 | 이 가게를 온/오프라인에서 어떻게 홍보하나 | 이 아이템이 이 상권에서 **통하는지 어떻게 판정하나** |
| 입력 | `StoreProfile` — 상호·리뷰·사진·메뉴·키워드 (+ 중첩 `VenturePlan`) | `ProgramBrief` — 아이템·업종·**검증 방식**·**단계**·가설·기간·예산 구간·차별점 (+ 자리 `unit_id`·거점 `district_id` 참조) |
| 출력 | `StoreMarketing` — online · offline · tone_keywords | `ProgramPlan` — online(모객) · offline(자리·연계) · **signals(검증 지표)** |
| 근거 | 리뷰·메뉴 → 자리·상권 수치로 옮겨가던 중 | 자리(대장 사실) · 상권(Gold 수치) · 브리프(창업자 주장) 세 층, 따로 싣는다 |

둘의 공통점은 **아직 검증되지 않은 아이템 + 아직 확정되지 않은 자리**다. 리뷰·사진·메뉴는
그 자리에서 이미 장사해야 생기는 과거의 축적이라 입력으로 성립하지 않는다. 그래서 대상만
바꾼 것이 아니라 입력·출력 계약을 통째로 갈았다.

### 검증 방식 셋 — 판정 신호가 다르다

| `mode` | 형태 | 기간 안에 잴 수 있는 것 |
|---|---|---|
| `popup` 팝업스토어 | 빈 자리를 며칠~몇 주 빌린다 | 유입·체류·구매전환 |
| `soft_open` 가오픈 | 운영을 축소해 연다 | 객단가·회전·재료 소진·응대 부하 |
| `mvp` MVP 테스트 | 점포 없이 매대·예약·사전주문 | 사전 수요(전환율) |

같은 지표를 셋에 붙이면 둘에서 잴 수 없는 값이 된다 — 팝업에 재구매율을 물으면 기간 안에 못 잰다.
`stage`(`pre_founder`·`founder`)는 어조와 협업 주체를 가른다. 화면에서는 「내 사업」 목적이
기본값을 정한다(창업 → 예비창업자, 업종 바꾸기·상권 옮기기 → 기창업자).

### 검증 지표(signals)가 이 트랙의 결론이다

`ValidationSignal` = 지표명 · 측정 방법 · 목표선 · **기각 조건**. 네 칸 모두 필수다.
무엇을 세면 통했다고 할지 **시작 전에** 정하지 않은 검증은 결과를 보고 사후에 말을 맞추게
된다 — 판정이 아니라 지출이다. 그래서 규칙 기반 스텁도 방식별 지표를 채우고, 화면은 판정표를
채널 초안보다 **먼저** 둔다.

### HA 가드가 바뀐 곳 (`services/ha_guard.check_program`)

### ② 검색 트렌드 방향 오독 — 원인은 절단 아티팩트 + 해석 위임

상권 카피가 *"신사동을 찾는 발걸음이 다시 늘고 있는 요즘"* 이라고 썼는데 입력은 하락이었다.
원인이 두 겹이었다.

- **미완성 달**: 데이터랩 월 버킷의 마지막 달은 수집 시점까지의 부분합이다. 2026-07-18
  수집분의 7월이 신사동 63.4→35.6(56%)·가로수길 19.1→9.9(52%)로 찍혔는데 18/31일=58%
  라는 절단 비율과 거의 같았다. **급락이 아니라 집계 아티팩트였다** — 재수집으로 확인한
  7월 실제값은 63.9·19.2 다. → `build_gold._complete_trend_points` 가 잘라낸다.
- **해석 위임**: 프롬프트에 원시 수치만 실어 방향 판단을 LLM 에 맡겼다.
  → `marketing._trend_summary` 가 **최근 3개월 평균 vs 직전 3개월 평균**을 비교해

## 0-3. Humanistic Authority 후처리 검증 (2026-08-06)

§3-4 가 요구한 "프롬프트 **+ 후처리**로 검증" 중 후처리가 없었다. `ha_check` 는 **LLM 이
스스로 "점검 통과"라고 적은 문장**이고 그게 사실인지 확인하는 코드는 한 줄도 없었다.
자기신고는 근거가 아니다 — 실측처럼 보이는 추정치를 가장 나쁜 산출물로 보는 것과 같은
이유다(AGENTS.md §0). `services/ha_guard.py` 가 그 검증을 한다.

### 두 등급으로 가른다

| 등급 | 판정 근거 | 처리 |
|---|---|---|
| **violation** | 입력과 대조하면 참·거짓이 갈린다 | **생성물 폐기** → 가게는 rule-stub, 상권은 시드 |
| **warning** | 사전 매칭이라 오탐이 섞인다 | 응답은 살리고 `ha_findings` 로 밝힌다 |

이 경계가 설계의 핵심이다. 전부 차단하면 최상급 표현 오탐 하나에 생성물 전체가 버려지고
크레딧을 쓴 호출이 통째로 낭비된다. 전부 표기만 하면 지어낸 가격이 화면까지 나간다.
2026-08-01 동명이지 정제에서 체험단 필터를 포기한 판단이 그대로 적용된다 — **자동 규칙을
세게 걸면 진짜 산출물까지 죽는다.**

### 검사 항목

| 코드 | 등급 | 잡는 것 |
|---|---|---|
| `fabricated_price` | violation | 입력에 없는 금액. 할인액·쿠폰액도 포함 — 얼마를 깎을지는 창업자 몫이다. (2026-09-17 부터 정본은 브리프 예산 구간 · 종전엔 점주 메뉴·리뷰) |
| `trend_contradiction` | violation | 서버가 확정한 트렌드 방향(하락·보합)을 뒤집는 유입 증가 주장 |
| `unsupported_superlative` | warning | 입력에 근거 없는 최상급("최고의") |
| `competitor_disparagement` | warning | 이웃 비교·출혈 경쟁 암시 — 공생 원칙 |
| `channel_concentration` | warning | 온라인 제안이 전부 한 플랫폼 계열 — 균형 원칙 |
| `missing_rationale` | warning | 근거가 비었거나 형식뿐인 제안 |
| `unproven_experience_claim` | violation | (2026-09-17) 단골·기존 고객·쌓인 후기를 전제한 제안. 측정 문장은 면제 — §0-V |
| `missing_validation_signal` · `unmeasurable_signal` · `missing_decision_rule` | warning | (2026-09-17) 검증 지표 없음 / 목표선에 셀 수 있는 값 없음 / 기각 조건 비어 있음 — §0-V |

### 오탐을 어디서 끊었나 (음성 대조로 고정)

규칙마다 **정상 표현이 죽지 않는지**를 테스트가 함께 붙든다. 이게 이 스위트의 절반이다.

- **주장과 목표를 가른다** — "손님이 늘고 있다"(주장)는 걸고 "손님을 **늘리는** 전단"(목표)은
  안 건다. 후자를 잡으면 정당한 오프라인 제안이 전부 죽는다.
- 트렌드에 **상승이 하나라도 섞이면** 증가 서술이 정당할 수 있어 판정하지 않는다.
- 최상급이 **입력에 이미 있으면 면제** — 리뷰에 "최고예요"가 있으면 인용할 근거가 있다.
- `최대한`은 `최대`가 아니고, `경쟁력`은 비방이 아니다.

### 알려진 한계

- 퍼센트 할인("10% 할인")은 금액 검사에 안 걸린다. 성격은 같지만 정상 표현과 구분이 어렵다.
- `1만 5천원` 같은 혼합 수 표기는 금액 파싱이 놓친다(`1만원`·`15,000원`은 잡는다).
- 사전 기반 검사는 우회가 쉽다 — **정직한 생성물을 확인하는 장치이지 적대적 입력을 막는
  장치가 아니다.**

### 검증 상태

`tests/test_ha_guard.py` 27건(규칙별 양성 + 오탐 음성 대조 + 배선). ⚠ **실제 LLM
생성물에 물려본 검증은 아직 못 했다** — 2026-08-06 현재 Anthropic 크레딧이 비어 있어
(400 `credit balance is too low`) LLM 경로 자체가 안 돈다. 충전 후 `PLACEOS_LIVE_LLM=1`
로 재확인이 필요하다.

## 0-4. 상권 행사를 생성 컨텍스트에 결합 (2026-08-06)

행사 785건이 Gold 에 있는데 `_district_context()` 가 blog_keyword·category·trend 만
싣고 있었다. 그래서 오프라인 제안이 *"상권 플리마켓/팝업 부스 참여"* 같은 **어느
상권에나 해당하는 말**로 나왔다. 실데이터를 수집해 놓고 쓰지 않으면 수집하지 않은 것과
같다. `marketing._events_context()` 가 이걸 컨텍스트 문장으로 만든다.

### 세 경우를 가른다 — 이게 요점이다

| 서비스 반환 | 뜻 | 컨텍스트 |
|---|---|---|
| `None` | 행사 Gold 미적재 | **아무 말도 하지 않는다** — 모르는 것을 "없다"고 하면 안 된다 |
| `[]` | 적재됐고 예정 행사 0건 | **없다고 말하고 제안을 금지한다** |
| 목록 | 예정 행사 있음 | 가까운 순 상위 5건 + **거리** |

빈 목록에 침묵하면 안 되는 이유가 핵심이다 — 아무 말도 안 하면 LLM 이 일반론으로 행사
참여를 지어낸다. 고치려던 바로 그 증상이다. 그래서 명시적으로 *"확인된 예정 행사가
없다. 행사 참여·연계를 제안하지 말 것"* 을 싣는다.

**거리를 반드시 싣는다.** 이 API 는 공공·문화시설 행사 중심이라 가두 상권 커버리지가
낮다 — 가로수길 2건은 둘 다 800m 밖(823m 논현글로벌평생학습센터, 957m 재즈클럽그루브)
이고, ikseon 은 78건에 최근접 113m 다. 거리를 빼면 남의 동네 행사가 "우리 골목 행사"로
둔갑한다. 도심 거점이 컨텍스트를 잠식하지 않게 상한 5건(`_MAX_CONTEXT_EVENTS`)을 뒀다.

### 함께 처리한 것 2건 (안 했으면 조용히 틀렸을 것)

- **캐시 무효화** — 컨텍스트 입력이 두 파일이 됐다. `_context_mtime` 이
  `program_content_context` 만 보면 **행사 파이프라인만 다시 돌린 경우 무효화가 안 돼**
  낡은 카피가 남는다. `events.source_mtime()` 을 키에 섞었다.
- **HA 금액 검증 오탐** — 행사 요금·기간의 숫자가 컨텍스트에 실린다. `check_store` 의
  금액 근거에 컨텍스트를 넣지 않으면 **정상 인용이 `fabricated_price` 로 폐기된다.**
  대가로 컨텍스트의 금액을 가게 가격처럼 쓰는 경우는 못 잡지만, 정상 인용을 죽이는
  쪽이 더 나쁘다.

검증: `tests/test_program_events_context.py` 9건(세 경우 분기 + 거리·상한·정렬 +
캐시 키 + HA 연계).

## 0-5. 상권 컨텍스트가 프로덕션에서 한 번도 돈 적이 없었다 (2026-08-06)

`_district_context()` 가 `import pandas` 로 시작해 파케이를 읽었다. **배포(Vercel
서버리스)에는 pandas 도 pyarrow 도 없다.** import 실패가 함수의 `except` 에 삼켜져
컨텍스트가 **항상 `None`** 이었고, `get_district_marketing` 은 `ctx` 가 없으면 LLM 을
아예 부르지 않으므로 — **상권 단위 LLM 경로는 프로덕션에서 단 한 번도 실행된 적이 없다.**
화면은 시드 카피를 보여주고 있었으므로 눈으로는 알 수 없었다. §0-4 에서 붙인 행사
컨텍스트도 같은 이유로 배포판에선 죽어 있었다.

**저장소는 이미 이 규칙을 알고 있었다** — `services/posting_inputs.py` 가
*"Vercel 서버리스에 pandas 를 싣지 않는다"* 라고 적어 두고 정적 JSON 만 읽는다.
런타임에 읽히는 다른 Gold 산출물(행사·입점입력·건물마스터·커버리지)도 전부
JSON/GeoJSON 이다. **이 산출물 하나만 예외였다.**

### 고친 방향 — 의존성을 넣지 않고 포맷을 바꿨다

pandas+pyarrow 를 배포에 추가하는 선택지도 있었지만 100MB 넘는 의존성을 서버리스
번들에 얹는 대가가 크다. 대신 산출물을 CSV 로 옮기고 **표준 라이브러리 `csv` 로 읽는다.**

- 3열 80행짜리 표에 파케이는 이득이 없다 — 실측 **174KB → 116KB 로 오히려 작아졌다.**
- 파케이는 **지웠다.** 두 벌로 두면 반드시 어긋난다(`data/.env` 이중화에서 배운 것과 같다).
- 파이프라인은 이 산출물만 `_save_csv()` 로 쓴다(다른 산출물은 파케이 유지 — 분석용이고
  런타임에 읽히지 않는다).
- `_trend_summary` 도 DataFrame 대신 `(기간키, 값)` 쌍을 받게 바꿨다.

회귀 방지 2건: `test_context_reads_without_pandas`(pandas import 를 막고 배포 환경을
흉내 낸다) + `test_context_artifact_is_csv_not_parquet`(파케이가 되살아나면 실패).

## 0-B. 대상 재정의에 따른 입력/출력 확정 (2026-08-16)

대상이 **공실에 창업할 기업**으로 바뀌면서 07-18 구조의 전제가 깨졌다. 5회 검증으로
세 요소를 확정한다.

### 대상
Platform(상권) 내 빈 Page(아직 입점하지 않은 공실 건물)에 Posting(창업)할 기업.

### 출력 — 둘은 대칭이 아니다. **주체가 다르다**

| | 온라인 | 오프라인 |
|---|---|---|
| 목적 | 신규 업체의 고객 획득(퍼포먼스) | **상권 전체**의 유동인구 확대 |
| 주체 | 창업 기업 **단독 실행** | 기업 + **상권 주체 협업**(상인회·구청·건물주) |
| 형태 | 채널·타겟·예산배분·목표지표 | 축제/플리마켓 — 시기·형식·협업 대상 |

오프라인이 상권 단위인 것이 설계를 규정한다. 신규 창업자 혼자 축제를 열 수 없다 —
실측하니 행사 785건 중 **57%가 공공·준공공 주최**(서울시청 97·마포문화재단 32·마포구청 28)다.
그래서 오프라인 출력은 "당신이 하세요"가 아니라 **"누구와 무엇을 제안하세요"** 여야 하고,
이는 HA 의 공생 원칙과 B2B 고객(지자체·자산운용사)에 동시에 닿는다.

### 입력 — 3층

1. **자리(Site)** 자동 — `unit_id` `lat/lng` `area` `floor` `was`(직전 업종) `건물 공실률`
   출처: `vacant_units.json`(**서빙 66거점 664유닛** — 2026-09-05 실측. 08-22 완주 당시엔 54거점 580유닛) → `page_building_master.geojson` 폴백
   ✅ **배선 완료 2026-08-23** — `services/program_site` + `GET /marketing/sites`,
   `StoreProfile.unit_id` 로 생성 입력에 합류. 선결이던 `.gitignore` 추적 예외도 같이 넣었다
2. **상권(Market)** 자동 — 임대료·유동등급·업종분포·블로그키워드·공실전망·행사
   \+ **TRDAR 수요신호**(§0-C) ← 두 출력의 공통 근거
3. **창업 계획(Venture)** 기업 입력 — 업종·목표고객·예산구간·개업예정일·내세울 강점
   \+ Posting 3-Tier 시나리오. **아직 없는 가게의 강점은 데이터에서 나올 수 없다.**
   이 층이 리뷰를 대신하는 근거의 원천이고, HA 의 `allowed_text` 가 된다.
   ✅ **배선 완료 2026-08-23 오후** — `services/program_venture` + `StoreProfile.venture`.
   상세는 §0-J.

### 설계 원칙 4가지 (검증에서 도출)

1. **근거는 리뷰가 아니라 수치다.** 리뷰 없는 입력을 현행 구현에 넣으면 근거란에
   "리뷰 키워드(리뷰 데이터 없음) 기반"이라는 자기모순이 나오고, "방문 후기형 포스팅"을
   공실에 제안한다(2026-08-16 실측). 근거의 종류를 바꿔야 해소된다.
2. **금액은 비율로만.** `_check_prices` 가 입력에 없는 금액을 violation 으로 응답을
   폐기한다. 기존 원칙("얼마를 깎을지는 점주 몫")과 같은 논리로 **"얼마를 쓸지는 기업 몫"** —
   비율만 제안하고 절대액은 ③층 예산에서 파생한다.
3. **"지어낸 행사"와 "제안하는 행사"를 가른다.** 현행 프롬프트는 신규 행사 제안을
   금지하는데(§0-4) 새 출력은 그것이 목적이다. 규칙을 없애지 말고 갈라야 한다 —
   기존 행사 **인용**은 사실 주장이라 컨텍스트 한정(현행 유지), 신규 행사 **제안**은
   계획이라 허용하되 **시간대 격차 수치 인용을 강제**한다.
4. **실행 주체를 명시한다.** 출력에 `actors` 를 두어 단독/협업을 가른다.

3층 입력의 마지막 층. ①자리·②상권은 우리 데이터에서 자동으로 나오지만 **③층은
기업이 넣는다** — 아직 없는 가게의 강점과 의도는 어떤 데이터에도 없다. 그래서 이
층만 수집 과제가 아니라 **계약·검증 과제**다.

|---|---|---|

| `budget_krw_min/max` | 월 예산 **구간** | HA allowed_text(절대액의 유일한 출처) |
| `open_date` | 개업 예정일 | **개업 전 확정 판정** |
| `strengths` | 내세울 강점(기업 주장) | 리뷰를 대신하는 근거 · allowed_text |
| `tier` | Posting 3-Tier 선택 | 회수 가정과 대조 |

### 이 층이 닫은 것 — '방문 후기형 포스팅'

§0-B 설계원칙 1 이 실측한 증상이다. 08-23 오전에 스텁 문구는 고쳤지만 판정 근거가
`reviews 가 비었는가` 라는 **추정**이었다 — 리뷰를 아직 못 모은 영업 중인 가게도
개업 전으로 오인된다. ③층의 개업예정일이 있으면 **확정**된다:

    is_pre_open()  →  True(개업 전) · False(영업 중) · **None(③층 없음 = 모른다)**

None 을 따로 두는 것이 핵심이다. False 로 뭉뚱그리면 ③층을 안 준 요청이 '영업 중'으로
단정돼 검사가 조용히 꺼지고, True 로 뭉뚱그리면 기존 요청이 전부 깨진다.

개업 전이 확정일 때만 `ha_guard._check_pre_open` 이 켜져서, 방문·후기·재방문·단골을
전제하는 생성물을 **violation(`pre_open_visit_claim`)으로 폐기**한다. 개업 당일은
영업 중으로 센다(경계에서 막히면 개업일 판촉을 못 한다).

### 금액은 ③층에만 절대액이 있다

출력의 `budget_share` 는 int 퍼센트라 절대액이 **구조적으로** 못 들어간다(§0-F).
예산의 절대액은 ③층에만 있고, 그 범위를 HA `allowed_text` 에 싣는다 — 넣지 않으면
기업이 준 예산을 인용한 문장이 '지어낸 금액'으로 폐기된다(행사 요금을 컨텍스트에
넣어야 했던 2026-08-06 과 같은 이유).

### 강점은 사실이 아니라 주장이다

`strengths` 는 검증되지 않았다. 점주가 준 리뷰·메뉴와 **같은 등급**으로 다뤄
allowed_text 에는 넣되, 컨텍스트에 "기업 주장, 검증된 사실 아님"이라고 밝혀 싣는다.
우리가 관측한 수치(①자리·②상권)와 같은 자리에 두면 생성물이 근거의 출처를 섞는다.
그래서 세 층을 프롬프트에도 **따로** 싣는다.

## 0-E. "문화행사 ≠ 상권 상업이벤트" 는 오진이었다 (2026-08-16)

§0-B 표에 "events 종류 불일치 → 외부 소스 필요"로 적었던 것을 정정한다. 근거 두 개가
모두 틀렸다.

**오류 ① 집계만 보고 판단했다.** 주최 분포(세종문화회관 105·서울도서관 31·시립미술관 30)를
보고 "공연장 프로그램이라 상권과 무관"으로 결론냈다. **거리로 걸러 열어보지 않았다.**
300m 안을 보면 성격이 다르다 — 서울아트위크(euljiro 59m·무료), DDP 바캉스 뮤직페스티벌
(dongdaemun 107m), **서울야외도서관/책읽는 서울광장**(cityhall 158m). 마지막 것은 광장
활성화 그 자체다. 축제 계열도 31건이 아니라 50건이다(분류를 좁게 잡았다).

**오류 ② 시각 정보가 없다고 했는데 있었다.** 원천에 `PRO_TIME` 이 **785/785** 채워져
있다("19:30", "10:00 ~ 19:00"). 690건이 파싱되는데 Gold 로 넘기지 않고 있었을 뿐이다.

즉 소스 문제가 아니라 **속성 누락 + 필터 부재**였고, 둘 다 저장소 안에서 고쳤다.

### 고친 것

- `build_events._time_bands()` — `PRO_TIME` → `tm`(시간대 밴드) + `time`(원문)을 Gold 에
  싣는다. 밴드 경계는 TRDAR 수요신호와 **같은 눈금**이다. 두 축이 같은 자로 재야
  교집합이 나온다. 시각을 못 읽으면 빈 목록이다(785건 중 97건) — 0시로 넘겨짚지 않는다.
- `_events_context(district_id, gap_band)` — 걸어갈 거리(`_WALKABLE_M=500`) 안으로
  거르고, **빈 시간대에 실제로 열리는 행사**를 먼저 보여준다. 없으면 없다고 밝힌다.
- 걸어갈 거리 안에 하나도 없으면 목록 대신 **연계 제안을 금지**한다(네 번째 경우).
  예전에는 957m 행사를 거리만 붙여 실었는데 그래도 "우리 골목 행사"처럼 쓰였다.
- 거리 미상(시드 잔재)은 '멀다'도 '가깝다'도 아니다 — 걸러내되, 거리가 있는 것이 하나도
  없으면 이들이라도 "거리 미상"으로 싣는다(정보를 버리지 않는다).

### 54거점 분포 (실측)

⚠ **2026-09-08 — 아래 표와 이어지는 "500m 안 28/54" 는 2026-08-16 · 54거점 시점 측정이고,
66거점으로 다시 재지 않았다.** 합이 54(17+11+24+2)인 것으로 확인된다. 그 뒤 더해진

| 경우 | 거점 수 |

이제 오프라인 제안이 "상권 플리마켓 참여" 같은 공허한 말 대신
**"6~11시가 +13.2%p 비어 있고, 274m 거리에서 그 시간대에 열리는 전시가 있다"**(cityhall)
가 된다. 근거 두 축이 처음으로 맞물린다.

### 그래도 남는 것

- **상업 이벤트 자체는 희소하다** — 플리마켓 2 · 장터 2 · **야시장 0**. 서울시 *문화*행사
  API 가 원천이라 상인회·전통시장 야시장은 애초에 안 들어온다. **신규 행사 제안**(§0-B의
  오프라인 (b) 모드)의 레퍼런스로 삼을 사례가 얇다 — 외부 소스가 필요한 건 여기뿐이다.
- **규모 미상** — 관람객 추정치가 없어 유입 효과를 정량화할 수 없다.
- 거리 중앙값 989m. 500m 안에 행사가 있는 거점은 28/54 다.

## 0-F. 출력 분리 배선 — 퍼포먼스 / 상권활성화 (2026-08-23)

§0-B 가 2026-08-16 에 **설계는 확정해 두었다**(주체가 다르다 · 금액은 비율로만 ·
행사는 인용과 제안을 가른다 · `actors` 로 단독/협업 구분). 없던 것은 판단이 아니라
배선이다. 그걸 넣었다.

### 왜 네 필드로는 안 됐나

`ChannelPlan` 은 `channel·kind·content·rationale` 넷이었다. 오프라인 제안에
**누가 함께하는지 적을 자리가 없다.** 그래서 출력이 "상권 플리마켓에 참여하세요"로
나왔는데, 신규 창업자는 혼자 축제를 열 수 없다 — 행사 785건 중 57%가 공공·준공공
주최다. 자리가 없으니 프롬프트를 아무리 고쳐도 담기지 않는 정보였다.

| | 온라인(퍼포먼스) | 오프라인(상권활성화) |
|---|---|---|
| 주체 | 창업 기업 **단독** | 기업 + **상권 주체 협업** |
| 추가 필드 | `target` · `budget_share` · `kpi` | `timing` · `actors` · `mode` |
| LLM 계약 | `LLMPerformancePlan` | `LLMActivationPlan` |

LLM 구조화 출력은 **둘로 갈랐고**(각자 필요한 필드만 요구), API 응답은 `ChannelPlan`
한 모양을 유지한다(새 필드는 전부 선택 — 프론트가 안 깨진다).

**예산은 `int` 퍼센트다.** "얼마를 쓸지는 기업 몫"(§0-B 원칙 2)을 프롬프트 문구가
아니라 **타입으로** 강제한다 — 문자열이면 LLM 이 "월 30만원"을 넣을 수 있지만
int 에는 넣을 수 없다. `test_budget_share_cannot_hold_absolute_amount` 가 고정한다.

### 행사 금지 조항 — 없애지 않고 갈랐다

2026-08-06 에 신규 행사 제안을 **통째로 금지**해서 지어낸 행사를 막았다(§0-4).
그런데 새 출력은 그것이 목적이다. 금지를 없애면 지어낸 행사가 돌아오고, 두면 새
출력을 못 만든다. §0-B 원칙 3 대로 `mode` 로 가른다:

| mode | 성격 | 규칙 |
|---|---|---|
| `cite` | 기존 행사 인용 = **사실 주장** | 컨텍스트에 실린 것만. 없다고 적혀 있으면 **violation** |
| `propose` | 신규 행사 제안 = **계획** | 허용. 단 빈 시간대 격차 수치 인용을 요구(warning) |

`cite` 검사는 **이름 대조를 하지 않는다.** 컨텍스트가 "확인된 예정 행사가 없다"·
"연계를 제안하지 말 것"이라고 못 박은 경우에만 위반으로 친다 — 그때는 인용할 것이
없다는 게 확정이라 오탐이 원리적으로 없다. 이름 매칭으로 넓히면 정상 인용을 죽인다
(2026-08-01 체험단 필터를 포기한 것과 같은 판단).

### 서버가 검증하는 것 4가지 (`ha_guard`)

스키마가 필드의 **존재**를 강제해도 내용이 규칙을 지켰는지는 서버가 본다 —
`ha_check` 가 자기신고라 근거가 아닌 것과 같은 이유다(§0-3).

| 코드 | 등급 | 잡는 것 |
|---|---|---|
| `fabricated_event` | violation | 인용할 행사가 없다는데 `mode=cite` |
| `unsupported_event_proposal` | warning | `mode=propose` 인데 빈 시간대 수치가 없다 |
| `missing_actors` | warning | 오프라인 제안에 협업 주체가 비었다 |
| `budget_share_mismatch` | warning | 온라인 예산 비율 합이 100%가 아니다 |

### 곁가지로 고친 것 — 공실에 "방문 후기형 포스팅"

폴백 스텁이 리뷰 유무와 무관하게 *"'{가게}' 방문 후기형 포스팅"* 을 제안했다.
§0-B 원칙 1 이 지적한 증상 그 자체다 — 아직 영업하지 않는 자리에 방문 후기를
제안하면 **있지도 않은 방문을 전제**한다. 리뷰가 비면 개업 예고·준비 과정으로
바꾸고 근거도 리뷰 대신 자리·상권 수치로 돌린다.

⚠ 이 시점에는 스텁만 고친 것이었다. 근본 해소인 입력 계약 ③층(창업계획)은 같은 날
오후 §0-J에서 배선됐고, 개업 전 방문·후기 전제를 `pre_open_visit_claim`으로 검증한다.

검증: `tests/test_program_output_split.py` 14건(계약 4 + 행사 분리 4 + 주체·예산 4 +
스텁 2). 기존 스위트의 `LLMChannelPlan` 사용처 35곳은 `conftest._perf` / `_act` 로 옮겼다.
