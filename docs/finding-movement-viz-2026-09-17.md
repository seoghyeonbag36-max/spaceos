# 발견 — 통신사 공공데이터 × SNS/IT 로 고객 **이동 동선**을 시각화할 수 있는가 (2026-09-17)

> 질문: "통신사 공공데이터를 쓸 수 있다면, 실제로 고객의 이동 동선을 SNS/IT 데이터로
> 시각화할 수 있는가." 6회 검증했다.
>
> 단일 기준은 문서가 아니라 산출물이다 — `python scripts/probe_movement_viz.py`
> (→ `reports/movement_viz_probe_2026-09-17.json`).

## 0. 결론 네 줄

1. **개인 동선(A→B→C 궤적)은 시각화할 수 없다.** 가려진 것이 아니라 **원천에 없다** —
   통신사 공개 데이터는 KT 가 비식별 **집계**로 만들어 배포한다. 열 10개 중 사람·트립을
   잇는 축이 **0개**다(P2).
2. **집계에서 되살릴 수도 없다.** 2×2 최소 표에서도 같은 집계를 내는 동선이 **3가지**,
   3×3 이면 **2,211가지**다. 최선의 추론(독립 결합)을 해도 왕복 인원을 10만 명 중
   **60,255명** 놓친다(P3).
3. **대신 '유입 흐름'은 그릴 수 있고, 체인은 이미 돈다.** 배포분과 같은 헤더의 합성
   4,000행을 흘렸더니 수집기→Gold 가 거점 3곳을 **24/24 시간 · 출발지 50곳**으로 채웠다.
   막는 것은 능력이 아니라 **취득(P1)과 화면(P6)**이다.
4. **SNS/IT 는 빠진 축을 메우지 못한다.** 소스 4종 중 (사람×좌표×시각)을 함께 주는 것이
   **0종**이고, Gold 산출물 487개 중 그 세 축을 한 레코드에 가진 파일도 **0개**다(P5).

**그래서 말을 바꿔 쓴다.** 앞으로 이 저장소·원고에서 "이동 동선"이라 적지 않는다.
실제로 있는 물건은 **유입 흐름(origin→hub flow)** 이다. 둘은 다른 것이고, 섞어 적으면
[KPI 누수](finding-kpi-leak-2026-09-16.md)와 같은 유형의 과대표기가 된다.

| 쓰지 말 것 | 쓸 것 | 왜 |
|---|---|---|
| 고객 이동 동선 · 궤적 · 경로 | **유입 흐름** · 유입 구성 | 개인 축이 없다(P2) |
| 동선 추적 · 방문 순서 | 도착시간대 분포 · 출발지 구성 | 순서가 원천에 없다(P3) |
| 거점 내 이동 | (없음) | 거점이 한 점으로 접힌다(P4) |

## 1. 용어부터 가른다 — 여기서 답이 갈린다

| | 동선(trajectory) | 유입 흐름(OD flow) |
|---|---|---|
| 정의 | 한 사람이 A→B→C 로 지난 **순서 있는 궤적** | 출발지별 도착 **인원 집계** |
| 필요한 축 | **개인 식별자** | 없어도 됨 |
| 답할 수 있는 질문 | "가로수길 온 사람이 다음에 어디 갔나" | "몇 시에 · 어디서 · 왜 왔나" |
| 통신사 공개 데이터 | **✗ 없다** | ✅ 있다 |

질문이 "동선"이라는 한 단어로 오면 답도 한 덩어리가 된다. 쪼개니 **하나는 불가, 하나는
가능**이었다. 아래 6회는 그 경계를 어디에 그을지 재는 작업이다.

### P1. 취득 — 지금 이 환경에서는 못 받는다 (그러나 그게 본질은 아니다)

| 배포처 | 결과 |
|---|---|
| `data.seoul.go.kr` (수도권 생활이동 OA-22300, 서울시×KT) | `403 Forbidden` (프록시 CONNECT 거부) |
| `openapi.seoul.go.kr:8088` (생활인구 REST) | timeout |
| `www.data.go.kr` (공공데이터포털 통신사 유동인구) | `403 Forbidden` |
| `sgisapi.kostat.go.kr` (통계청 경계) | `403 Forbidden` |
| `data.gg.go.kr` (경기 유입/유출 생활이동인구) | `403 Forbidden` |

⚠ **이 0/5 는 원격 실행 환경의 이그레스 정책이지 데이터의 성질이 아니다.** 로컬에서
키를 들고 돌리면 달라진다. 이 항목에서 낡지 않는 사실은 따로 있다:

> **OA-22300 은 REST 가 아니라 포털 로그인 뒤 ZIP 파일이다.** 키가 있어도 무인
> 수집이 되지 않는다 — `living_migration.py` 가 URL 이 아니라 **디렉터리**를 인자로
> 받는 이유가 이것이다.

그리고 저장소 실태: bronze 생활이동 원본 **0건**, `gold/platform_page_migration.json`
**없음**. 즉 이 트랙은 **한 번도 실데이터로 돈 적이 없다.**

### P2. 식별자 — 동선은 가려진 게 아니라 없다

배포분 헤더 매핑표(`living_migration.py::_COLS`)가 스키마의 단일 기준이다.

| 축 | 열 |
|---|---|
| 시간 | 대상연월 · 요일 · 도착시간 |
| 공간 | 출발행정동 · 도착행정동 |
| 속성 | 성별 · 나이 · 이동유형 |
| 값 | 평균 이동시간 · 이동인구 |
| **개인** | **없음 (0/10)** |

한 행이 말하는 것은 *"이 시각에 A동 → B동으로 n명"* 이다. *"누가 어디를 거쳐 갔다"*가
아니다. 사람을 이을 열이 없으므로 **두 번째 다리(B→C)를 첫 번째 다리(A→B)와 묶을 수
없다.** 동선은 마스킹된 것이 아니라 **생산 단계에서 존재하지 않는다.**

⚠ 이동인구가 `*`(KT 비식별)인 행이 따로 있다. 그건 값의 마스킹이고, 위 결론은 그것과
무관하게 **스키마 차원**에서 성립한다.

### P3. 복원 — 집계는 동선을 결정하지 않는다

"집계에서 역산하면 되지 않나"에 대한 답. O→H(도착) 와 H→D(출발) 두 주변분포만 주어졌을
때, 그것과 모순 없는 2구간 동선이 몇 가지인지 **정확히 셌다**.

| 표 크기 | 각 변 인원 | 같은 집계를 내는 동선 |
|---|---|---|
| 2×2 | 2 | **3가지** |
| 2×2 | 5 | **6가지** |
| 3×3 | 10 | **2,211가지** |

**최소 표에서 이미 유일하지 않다.** 실제 규모(출발지 50곳 × 도착지 50곳 × 24시간 ×
이동유형 7종)에서는 셀 필요도 없다.

그리고 "결정되지 않는 것을 최선으로 추론"하면 얼마나 틀리는가 — 유입 10만 명, 출발지
50곳, 귀가 비율 0.62 로 두고 진짜 결합과 독립 결합을 비교했다:

| | 값 |
|---|---|
| 총변동거리(TV) | **0.603** |
| 실제 왕복 비중 | 0.631 |
| 추론된 왕복 비중 | 0.028 |
| **놓치는 왕복 인원** | **60,255 / 100,000명** |

⚠ 진짜 결합은 시뮬레이션이다 — **그것이 곧 요점이다.** 원천은 주변분포 둘만 주고,
결합은 어떤 모양이든 될 수 있다. 사람이 대개 왔던 곳으로 돌아간다는 **가장 흔한 사실
하나**만으로도 독립 가정이 60%를 날린다.

### P4. 해상도 — 거점은 통째로 한 점이 된다

| | 값 | 출처 |
|---|---|---|
| 거점 수 | 66 | `gold/page_footfall_hourly.json` |
| 거점당 행정동 | min 1 · **중앙 4** · 평균 3.94 · max 11 | 같음 |
| 거점이 최대 행정동을 차지하는 비중 | 중앙 **0.689** | 같음 |
| **거점 내부 이동 노드** | **1** | 위에서 유도 |
| (대조) 체류 레이어 셀/거점 | **68** (집계구 27) | `silver/cell_jipgyegu.json` |
| (대조) 공실 유닛 | 617 | `silver/unit_jipgyegu.json` |

이동 데이터의 최소 공간 단위는 **행정동**이고, 거점은 행정동보다 **작다**(중앙값으로
행정동의 0.689). 그래서 거점 안에서 출발지·도착지가 갈리지 않는다 — **내부 이동이 0개로
접힌다.** 같은 거점을 체류(유동) 레이어는 셀 68개로 가른다. **68 대 1** 이다.

→ "어느 건물 앞을 지나 어느 가게로 들어갔나"는 이 데이터로 영원히 못 그린다. 공간
해상도의 문제이고, [finding-foot-traffic-resolution.md](finding-foot-traffic-resolution.md)
가 `foot` 에서 겪은 것과 같은 벽이다.

### P5. SNS/IT — 결손이 서로를 메우지 못한다

| 소스 | 레코드 입도 | 사람 | 좌표 | 시각 |
|---|---|---|---|---|
| 네이버 블로그 검색 | 문서(포스트) | ✗ | ✗ | 작성일 |
| 네이버 데이터랩 | 키워드×기간 **상대비율** | ✗ | ✗ | 월 |
| 인스타 Graph 해시태그 | 해시태그 집계 | ✗ | ✗ | 최근 |
| 카카오 로컬 | POI | ✗ | ✅ | ✗ |
| **3축 동시 보유** | | | | **0종** |

Gold 산출물 **487개 전수** 스캔: 작성자/사용자 키를 가진 파일 **0개**, 좌표·시각까지 함께
가진 파일 **0개**.

구조를 한 줄로: **SNS 는 "어디서 말했나"를 모르고**(좌표 없음), **지도/검색은 "누가
갔나"를 모른다**(개인 축 없음). 두 결손이 직교하지 않고 **같은 축(사람)에서 겹친다** —
그래서 합쳐도 동선이 되지 않는다.

⚠ 카카오 로컬은 좌표를 주지만 **장소의 좌표**이지 사람의 방문이 아니다. 게다가 약관상
응답 저장이 금지다([finding-map-provider-google-2026-09-15.md](finding-map-provider-google-2026-09-15.md) §7-2).

### P6. 시각화 — 체인은 돈다, 화면이 없다

배포분과 **같은 헤더**의 합성 CSV 4,000행을 실제 수집기·파이프라인에 흘렸다
(값은 가짜, 형식은 진짜. 임시 디렉터리에만 쓰고 저장소 bronze/gold 는 건드리지 않는다).

```
합성 4,000행 → living_migration.collect() → bronze 3거점
             → build_page_migration.run()  → gold/platform_page_migration.json (12KB)
```

| 측정 | 값 |
|---|---|
| 체인 동작 | ✅ 거점 3/3 |
| 채워진 시간 축 | **24/24** |
| 출발지 | **50곳** (수집기 `origin_top` 상한) |
| 채워진 축 | `by_hour` · `hour_share` · `peak` · `purpose_share` · `sex_age_share` · `origin_top` · `adong` |
| 유선용 행정동 좌표 보유 | **163개** |
| 서빙 엔드포인트 | **없음** |
| 프론트 레이어 | **없음** |

**즉 데이터만 오면 "몇 시에 · 어디서 · 왜 왔나"는 바로 그릴 수 있다.** 못 그리는 것은
"어디를 거쳐 갔나" 하나다.

⚠ 좌표 163개는 **우리 거점이 걸친 행정동**에서 모은 것이다. 실데이터의 출발지는
수도권 전역이라 대부분이 좌표 없이 온다 — 유선(flow line)을 그리려면 **행정동 중심좌표
전량**이 따로 필요하다(분모는 이 환경에서 측정 못 했다. 네트워크 차단).

## 3. 결정

### 3-1. "이동 동선"이라는 표기를 걷어낸다

§0 의 표대로 **유입 흐름**으로 바꿔 적는다. 공모전 원고에도 같은 규칙을 적용한다
(`python scripts/check_application.py` 가 `docs/apply/claims.json` 밖 수치를 잡는다 —
이 문서의 수치는 근거로 인용 가능하다).

### 3-2. 그릴 것은 유선이 아니라 **유입 구성**이다

동선이 없으므로 궤적선을 그릴 수 없고, 거점 내부 해상도가 1 이므로 거점 안에 흐름을
그릴 수도 없다. 남는 것은 **거점 하나를 도착점으로 둔 유입 구성**이다.

| 화면 | 데이터 | 상태 |
|---|---|---|
| 도착시간 24시간 곡선 | `by_hour` · `peak` | Gold 준비됨 · 화면 없음 |
| 이동유형 7종 구성 | `purpose_share` | 같음 |
| 성·연령 구성 | `sex_age_share` | 같음 |
| 출발지 상위 50 (유선/코로플레스) | `origin_top` | 좌표 163개만 보유 |

⚠ 유선으로 그릴 때 **선이 실제 이동 경로처럼 읽히면 안 된다.** 그것은 출발지와
도착지를 잇는 **집계의 표현**이지 지나간 길이 아니다. `resolution: "adong"` 을 응답에
싣는 기존 규칙에 더해, 화면에 그 문구를 띄운다.

### 3-3. 순서 — 막는 것은 능력이 아니라 이 둘이다

1. **취득** — OA-22300 ZIP 을 사람이 내려받아 `SEOUL_MIGRATION_DIR` 에 둔다.
   자동화 불가(로그인). ⛔ 이 세션에서는 불가(이그레스 차단).
2. **`silver/hub_adong.json`** — gitignore 라 이 환경에 없다. 다만 **그 내용은
   `gold/page_footfall_hourly.json` 의 `adong` 필드에 이미 실려 있다**(66거점 187코드).
   P6 는 그걸로 되살려 체인을 돌렸다 — `build_hub_adong` 재실행(카카오 키)이 필수 경로가
   아님을 뜻한다.
3. **서빙** — `api/v1/heatmap.py` 에 `migration` 이 없다. `footfall` 옆에 붙인다.
4. **화면** — 프론트에 레이어가 없다. §3-2 의 네 화면.
5. **행정동 중심좌표 전량** — 유선을 그릴 때만 필요. 없으면 상위 출발지 목록으로 대체.

### 3-4. 낡지 않게 하는 장치

- 판정의 단일 기준은 `scripts/probe_movement_viz.py` 다. 문서가 아니라 이것을 다시 돌린다.
- P2·P6 는 `data/tests/test_movement_viz.py` 가 고정한다 — 스키마에 개인 축이 생기거나
  체인이 깨지면 테스트가 먼저 깨진다.
