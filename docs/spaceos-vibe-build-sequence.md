### 2026-09-04 — 서울 2차 12거점이 Page 밖 세 트랙에 들어왔다

08-30 에 Page(Tier1)까지 서고 09-03 에 서빙에 오른 12거점이, **Platform·Posting·Program
산출물에서는 통째로 빠져 있었다**(전부 54/66). 수집 부족이 아니라 `DISTRICT_TRDAR`·
`DISTRICT_PLACES` 매핑이 비어 파이프라인이 그 거점을 **안 돌았다.** 매핑을 채우고 체인을
다시 밀어 전부 66/66 이 됐다(거점 시계열 · 노드 47,442 · Program CSV · 유동/밀도 ·
Posting 입력 · LSTM forecast · GNN 추천).

**같은 양식을 네 번 더 만났다 — 전부 "재료는 있는데 안 읽거나 안 돈다" 였다.**

1. `build_trdar_demand` 가 체인에 없었다. `build_gold --platform13` 안에 있을 것 같지만
   **별도 빌더**라, 빼면 `trdar_demand.parquet` 가 54에 머물러 유동·밀도 레이어와 GNN
   `_demand` 블록이 12거점을 못 본다.
2. `build_program_demand` 도 마찬가지다. `build_gold` 가 `program_content_context.csv` 를
   통째로 다시 쓰므로 그 CSV 에 행을 얹는 빌더는 **gold 뒤에 전부** 와야 한다
   (`trend` 는 넣고 `demand` 를 빠뜨려 게이트가 81.8% → 1.5% 로 떨어졌다).
3. `services/districts.resolved_units()` 가 시드 54(`DISTRICTS_BY_ID`)를 문지기로 써서,
   12거점이 인벤토리 136유닛과 R-ONE 입력을 **다 갖추고도** Posting 이 통째로 비었다.
   진행률로는 안 보였다 — 그 게이트는 gold 파일을 세지 서빙이 읽는지는 안 본다.
4. `pppp_status._count_measured_foot_hubs()` 도 시드 54를 돌아 **구조적으로 54를 못 넘었다.**
   `foot 66/66` 인데 '거점 내 서열 실측 54/66' 으로 찍힌 것이 그 때문이다.

**곁가지로 LSTM 이 66거점에서 학습 불능이었다.** `datasets.build_dataset` 이 패널 전체로
`feats.mean(axis=0)` 을 내는데, R-ONE 계열에 NaN 이 하나만 있어도 그 열의 평균·표준편차가
NaN 이 되어 표준화가 **모든 거점의 모든 샘플**을 오염시킨다. 결측 **18칸이 1,452행 학습을
죽여** 8 trial 이 전부 `MAE nan · 방향정확도 0.0%` 로 나왔다(kkachisan 14분기 · sangbong
4분기 — 그 상권의 R-ONE 시계열이 늦게 시작한다). `nanmean`/`nanstd` 로 바꾸고 결측이 낀
학습 윈도우는 **채우지 않고 뺐다** — 결측이 전부 시계열 앞쪽이라 예측 기준 윈도우는
온전하고, 그래서 **예측을 잃은 거점은 0곳**이다(66/66 forecast).

⚠ 거점 수에 절대값으로 묶인 기준은 거점이 늘 때마다 깨진다. 이번에 둘을 비율로 바꿨다

## 원칙
- **1단계 = 1 바이브 사이클**: PRD(자연어) → AI 코드 생성(Cursor/Claude Code + 슬래시 명령) → `/verify` 검증.
- **데이터 흐름**: Bronze(수집) → Silver(정제·매칭) → Gold(분석·GeoJSON). `/api/v1/...` 규약.
- **데이터가 UI를 결정(회의 3번)**: 먼저 데이터를 확보하고, 지도 위 표현 방식을 그 데이터로 결정.

**거점 단위 실데이터를 유닛에 내릴 때 두 번 보정이 필요했다.** 둘 다 "실데이터가 절대

- **층 계수** — R-ONE 소규모상가 임대료는 사실상 1층 기준이다. 시드 270유닛과 대조하니
  R-ONE환산/시드 비율이 층수를 따라 단조 증가했다(1F 1.69 · 2F 3.66 · 3F 3.83 · 4F 5.25 ·
  6F 6.84 · 7F 8.17). 그대로 곱하면 상층 임대료를 2~8배 과대계상한다. 계수 적용 후 층별
  배수가 1.5~2.0으로 평탄해졌다. **이 계수는 실측이 아니라 계수다.**
- **거점 내 서열(당시 방식)** — flpop 은 거점 단위라 그대로 내리면 한 거점의 모든 유닛이 같은 등급이
  된다(가로수길 고/고/중/저/중 → 전부 중, 등급 변경 179/270유닛). flpop 3분위로 거점
  기준 등급을 정하고 시드의 거점 내 상대 위치로 ±1칸 이동시키니 구조가 보존됐다(변경 111/270).

  **후속 해소(08-25):** 이 `flpop+seed` 방식은 집계구 생활인구 PIP 배정으로 교체됐다.

  출처는 `flpop+jipgyegu`다. 위 270유닛·±1칸 수치는 교체 전 대조 기록이다.

**출처 표기 필수**: 응답의 `inputs_source`가 현재 각 축을 구분한다 — `rent='rone'`,

### 6-2 후속 — Program 상용 입력 온보딩 계약 (2026-08-29)

공개 데모 `POST /api/v1/marketing/generate`는 유지하면서, 점주 또는 권한을 받은 조직의
입력만 받는 `POST /api/v1/marketing/onboarding/generate`를 분리했다. 이 경로는 JWT 또는
조직 API key 인증이 필수이고 다음 계약을 모두 충족하지 않으면 실패한다.

- 입력 출처는 `merchant-provided`, 목적은 `program-marketing-generation`, 계약 버전은
  `spaceos.program-onboarding/1`로 고정한다.
- 처리 동의·제공 권한 확인·외부 모델 처리 동의를 각각 명시적으로 받고, 원문 보존은
  `request-only`만 허용한다. 기본값으로 동의를 채우지 않는다.
- 공개 블로그 검색 스니펫은 별도 상태로 두어 상용 요청에 섞이지 않는다. 상용 모드에는
  점주가 직접 넣은 리뷰·사진·메뉴·키워드·창업계획 중 하나가 반드시 있어야 한다.
- 애플리케이션 DB에는 원문을 저장하지 않는다. 조직·계약 버전·거점·항목별 건수만 감사
  메타데이터로 남기고, 응답은 조직별 동의 영수증과 `raw_input_persisted=false`를 돌려준다.

통과 조건은 `apps/backend/tests/test_program_commercial_onboarding.py`의 인증 거절, 불완전
동의 거절, 빈 입력 거절, 원문 비저장 영수증, 조직 격리, JWT/API key 두 경로 테스트 6건과
프론트 타입체크 빌드다. 이것은 **상용 입력을 받을 기술 계약의 완료**이지 실제 기업이 쓰고
가치를 확인했다는 뜻이 아니다. PMF 판정은 별도의 B2B 파일럿과 `active_orgs`로만 한다.
