## 원칙
- **1단계 = 1 바이브 사이클**: PRD(자연어) → AI 코드 생성(Cursor/Claude Code + 슬래시 명령) → `/verify` 검증.
- **데이터 흐름**: Bronze(수집) → Silver(정제·매칭) → Gold(분석·GeoJSON). `/api/v1/...` 규약.
- **데이터가 UI를 결정(회의 3번)**: 먼저 데이터를 확보하고, 지도 위 표현 방식을 그 데이터로 결정.
- **회의 1번(네이버 지도 확대)**은 데이터와 독립 → 언제든 병렬 착수 가능.

### Phase 1 재진입 — 거점 확장이 현재의 실제 작업 (2026-08-08~16)

Page 는 Phase 4 를 통과한 뒤 **다시 Phase 1 로 내려와** 거점 수를 늘리는 중이다.
만드는 단계가 아니라 채우는 단계이고, 속도를 정하는 것은 코드가 아니라 **API 쿼터**다.

| 구분 | 거점 수 | 근거 |
|---|---|---|
| **Tier1(대장 실측)** | **49** | 건축HUB 표제부·전유부 수집 완료 — 08-08 에 13→22, 08-15 에 22→40, 08-16 에 40→49 |
| **Tier2(폴리곤 기반)** | 5 | `hyehwa` · `kyunghee` · `sadang` · `sukmyung` · `wangsimni` |
| 합계 | **54** | `gold/*/coverage.json` 의 `tier` 가 단일 기준 |

**Tier1 이라고 다 같지 않다.** 대표 집계 커버리지(`reference_coverage_pct`)는 49거점
중앙값 **96.4%**, 46곳이 90% 이상이지만 아래가 남는다 — 티어는 통과/미통과이지 품질
등급이 아니므로, 거점을 인용할 때 이 값을 같이 본다.

| 거점 | 대표 집계 커버리지 | 사유 |
|---|---|---|
| `dongdaemun` | **24.3%** | 페이지 캡(`_EXPOS_FULL_MAX=300`)을 건 거점 — 콜을 34,600 → 3,900 으로 줄인 대가다 |
| `yongsan` | 81.0% | 층별개요 미완 |
| `samcheong` | 89.5% | 층별개요 미완 |

**같은 기간에 고친 집계 결함 3건** — 모두 값이 이미 틀려 있던 건이다.

- **지번 단위 집계로 교정**: 거점 공실을 폴리곤(동) 단위로 세어 한 지번의 여러 동이
  중복 가중되고 있었다. 건물 이력도 같은 결함이라 동마다 복제됐다(66MB → 27MB).
- **건축HUB 5xx·비JSON 을 DNS 블립과 분리**: 서버 장애를 네트워크 블립으로 오인해
  같은 백오프를 태우고 있었다 → 속도 5배 + 데이터 유실 차단.
- **Gold ignore 예외 확장자 정정**: 상권 컨텍스트가 프로덕션에서만 조용히 무동작.

### 병목 — 건축HUB 전유부 쿼터 (2026-08-09)

일 10,000콜(무료·자동승인)이 확장 속도의 상한이다. 최적화를 프로브로 검증한 결과:

- `numOfRows` 는 **서버가 100 에서 하드캡**한다(10~20000 프로브 전수 확인).
  페이지를 키워 콜을 줄이는 길은 없고, 줄일 수 있는 건 페이지 **수**뿐이다.
- 페이지 캡(`_EXPOS_FULL_MAX = 300`)을 도입 — dongdaemun 34,600 → 3,900콜.
  한 번 기각했다가 되살렸다. 코퍼스 **평균**으로는 이득이 작지만 **거점 편차**가
  결정을 뒤집었다.
- 전유부 capacity 는 `capacity_method == "expos_units"`(집합건물)라 **대표 집계에
  쓰이지 않는다**(`_COUNTED_METHODS = {"floor_ouln"}`). 콜은 정반대로 쏠려 있었다.

→ 상세: [finding-expos-quota-2026-08-09.md](finding-expos-quota-2026-08-09.md)

⚠ 대장 수집은 **AC 전원 필수** — 배터리 구동 시 약 7배 느려지고 덮개를 닫으면 정지한다.

### 3-1 결과 — 시드/합성 → Gold 실측 배선 (2026-08-01)
`services/districts.build_cells()` 의 `sin()` 해시 합성이 거점 공실의 유일한 출처였다.
이제 Gold 건물 마스터가 있는 거점은 실측 집계를 쓰고, 없는 거점만 합성으로 폴백한다.

- **적용 범위**: 54거점 중 Gold 보유 **13거점**이 실측. 나머지 41거점은 합성 유지 —
  `data/pipelines/build_page_master.py` 로 Gold 를 만들면 코드 수정 없이 자동 전환된다.
  > **갱신 2026-08-16**: 이 "13거점"은 08-01 시점 값이다. 현재 **Tier1 49 · Tier2 5**
  > 로 54거점 전부가 Gold 를 갖는다. 위 문단의 자동 전환 설계가 의도대로 동작한 결과다.
- **집계 규칙 3종** (`services/gold_vacancy.py`, `calibration.json` 과 동일 기준):
  | # | 배제 대상 | 이유 |
  |---|---|---|
  | 1 | `capacity_method == floor_approx` | 지상 **전체** 층수 근사 → 주거·사무층까지 상가로 세어 분모가 부푼다 (가로수길 전수 33.1% vs 24.2%) |
  | 2 | `capacity_method == expos_units` (집합건물) | 상가정보가 집합상가 **내부** 점포를 그 건물 bdMgtSn 으로 귀속시키지 못해 분자가 빈다 → 공실률 78~86% |
  | 3 | `source == polygon_only` | 점포 미매칭이라 `active=0`, 공실률 100% 고정 |
  세 규칙은 서로 독립이라 각각 검사한다(재빌드가 조합을 바꿀 수 있다).
- **출처 표기 필수**: 응답의 `vacancy_source`("gold"/"synthetic")를 프론트가 배지로 노출한다.
  합성값이 실측처럼 읽히면 안 된다.
- **격자**: 셀 크기·원점은 시드 grid 를 그대로 쓰되 인덱스가 bb 밖으로 나갈 수 있게 두어,
  수집 반경이 시드 bb 를 벗어난 건물을 버리지 않는다(가로수길 72셀 중 일부가 bb 밖).

### 3-1 앵커 대조 (2026-08-01) — 집합건물 혼입이 대표값을 무너뜨리고 있었다
초판 배선은 규칙 1·3만 적용해 집합건물을 섞었고, 5거점이 50~67% 로 튀었다.
`python -m data.pipelines.calibrate_vacancy <거점>` 으로 앵커 대조한 결과 원인이 확정됐다:
**집합건물은 건물 수로는 소수인데 호실이 많아 분모의 52~82% 를 차지**한다.

| 거점 | 혼합(초판) | 일반만(현재) | R-ONE 앵커 | 격차 | 집합이 분모에서 |
|---|---|---|---|---|---|
| seoulsup | 67.0% | **19.8%** | 3.4% | +16.4%p | 82% |
| ikseon | 57.1% | **30.1%** | 8.5% | +21.5%p | 52% |
| myeongdong | 56.3% | **16.9%** | 5.0% | +11.9%p | 59% |
| yeonnam | 52.3% | **16.6%** | 4.5% | +12.1%p | 52% |
| euljiro | 51.3% | **17.7%** | 6.8% | +10.9%p | 53% |

13거점 전체 범위: **13.3~30.1%**, 앵커 격차 **-4.0 ~ +21.5%p**
(itaewon +0.4 · hannam +2.0 · garosugil +3.2 가 가장 정합, songridan 은 -4.0 으로 과소).
격차가 0 이 되는 것이 정상은 아니다 — 우리는 호실·전수, R-ONE 은 면적·표본이라
모집단이 다르다. 절대값이 아니라 **거점 간 비교·추세 감시**에 쓴다.
API 는 `anchor_pct` / `anchor_gap_pp` 로 이 대조를 함께 내려보낸다.

> **갱신 2026-08-16**: 위 범위는 **13거점 시절 값이다.** 앵커가 40거점으로 산출된
> 현재(`GET /commercial-districts` 실측)는 54거점 중 **앵커 보유 40거점**, 공실률
> **3.1~33.5%**, 격차 **-12.3 ~ +27.9%p** 로 양쪽이 다 벌어졌다(최소 dongdaemun -12.3 ·
> 최대 nokdu +27.9, garosugil 은 +2.9 로 여전히 정합). 나머지 14거점은 `calibration.json`
> 이 없어 **대조 자체가 안 된다** — 격차 0 이라는 뜻이 아니다.
> ⚠ dongdaemun 의 -12.3 은 정합이 좋아진 것이 아니라 대표 집계 커버리지가 24.3% 라
> 분모가 덜 찬 것이다. 격차는 커버리지와 함께 읽어야 한다.

⚠ 집합건물 공실률 자체는 여전히 신뢰 구간 밖이다. 층·호 단위 매칭(flrNo/hoNo)을
붙이기 전까지 대표 집계에서 뺀 채로 둔다(건물 폴리곤 레이어에는 계속 그린다).
13거점 시절 최대 격차는 ikseon +21.5%p 였다 — 익선동은 한옥 소형 호실이 많아 호실
기준이 면적 기준보다 높게 나오는 것으로 보이나, 확인은 미실시.
40거점으로 넓힌 지금 최대는 **nokdu +27.9%p** 이고 ikseon 은 +21.1 로 2위다(08-16).
노량진·녹두 계열이 위로 올라온 이유는 미확인 — ikseon 과 같은 소형 호실 가설이
맞는지 따로 봐야 한다.

외부 코파일럿 명세가 아직 없어 실제로는 **항상 3-Tier 폴백**이 돈다. 그래서 어댑터를
기다리는 대신 **폴백의 입력**을 실데이터로 올렸다. 신규 파이프라인
`data/pipelines/build_posting_inputs.py` → `gold/platform_posting_inputs.json`,
서빙은 `apps/backend/app/services/posting_inputs.py`.

| 입력 | 소스 | 상태 |
|---|---|---|
| `rent` 월임대료 | R-ONE 소규모상가 임대료 × 면적 × **층 계수** | ✅ 실데이터 |
| `foot` 유동인구 | 서울 상권분석 유동인구 3분위 + **거점 내 시드 서열** | ◐ 혼합 |
| `area` 면적 | 없음 — silver `com_area_flr` 은 건물 단위지 유닛 단위가 아니다 | ⬜ 시드 |
| `prem` 권리금 | 거점 단위 소스 없음 — 통계(142006)는 있으나 **전국 7,000 표본**이라 해상도 부족(2026-08-09 정정) | ⬜ 시드 |

**거점 단위 실데이터를 유닛에 내릴 때 두 번 보정이 필요했다.** 둘 다 "실데이터가 절대
수준을, 계수가 거점 내 구조를" 맡는 형태다.

- **층 계수** — R-ONE 소규모상가 임대료는 사실상 1층 기준이다. 시드 270유닛과 대조하니
  R-ONE환산/시드 비율이 층수를 따라 단조 증가했다(1F 1.69 · 2F 3.66 · 3F 3.83 · 4F 5.25 ·
  6F 6.84 · 7F 8.17). 그대로 곱하면 상층 임대료를 2~8배 과대계상한다. 계수 적용 후 층별
  배수가 1.5~2.0으로 평탄해졌다. **이 계수는 실측이 아니라 계수다.**
- **거점 내 서열** — flpop 은 거점 단위라 그대로 내리면 한 거점의 모든 유닛이 같은 등급이
  된다(가로수길 고/고/중/저/중 → 전부 중, 등급 변경 179/270유닛). flpop 3분위로 거점
  기준 등급을 정하고 시드의 거점 내 상대 위치로 ±1칸 이동시키니 구조가 보존됐다(변경 111/270).

**출처 표기 필수**: 응답의 `inputs_source` 가 필드별 출처(`rone`/`flpop+seed`/`seed`)를
밝히고, 프론트 유닛 카드가 `R-ONE`·`유동인구`(초록) / `추정`(회색 점선) 배지로 노출한다.

**음성 대조**: 층 계수를 전부 1.0 으로 무력화하니 `test_rent_falls_with_floor` 가
`garosugil 3F 평당 24.5 >= 1F` 로 정확히 실패했다.

⚠ **함께 고친 선행 버그 — 회수기간 단위 혼용**: `tier_scenarios.roi()` 가
`invest(백만원) / net(만원)` 이라 회수기간이 100배 작게 나왔다(화면에 "회수 0개월 /
0.1개월"). `invest × 100 / net` 으로 교정 → 1.4~29.8개월. 실데이터를 넣은 바로 그
계산식이라 함께 처리했다.

⚠ **함께 고친 성능 문제 — 상권 콘텐츠 LLM 무캐시**: 크레딧 충전으로 LLM 경로가 살아나면서
`/marketing/{id}` 가 **호출마다** LLM 을 쳤다(실측 12~17초 + 매번 크레딧). 거점 심층 뷰가
이 응답을 기다려 화면이 멈췄다. 입력이 Gold 컨텍스트 파일 하나뿐이라 mtime 기준 캐시를
붙였다 → 첫 호출 17.6초, 이후 **0.03초**. 테스트 격리용 `clear_district_cache()` 공개.

⚠ `rec` 을 정하는 자리에서 **`prem` 포함 여부도 함께 확정**해야 한다. 회수 최단이면
