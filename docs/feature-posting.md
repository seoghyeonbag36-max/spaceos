> **2026-07-18 개정**: 자체 비용-효용 계산 대신 **외부에서 만든 AI 창업 코파일럿 프로그램을 연동해 적용**하는 것을 1순위로 한다. 내부 3-Tier(고급화/가성비/기능중심) 계산은 폴백·검증용으로 유지.

### 0-A. 증상 — 08-22 전수 재측정 (문서의 이전 수치는 낡았었다)

실 유닛 **270건 전수** + 파라미터 **37,800 조합** 스윕:

| 항목 | 이전 기재 | **08-22 실측** |
|---|---|---|
| 마진(premium/value/factory 중앙) | 51~73% | **70.2 / 63.4 / 45.8%** |
| 회수기간 | 0.5~1.6개월 | **중앙 1.8개월** (1.1~14.6) |
| factory 1위 | 0건 | 실 유닛 **0/270**, 스윕 8/37,800(0.02%) |

이전 수치는 `rent` 가 R-ONE 실데이터로 바뀌기 전 값이다. 증상의 방향은 같지만 폭이 다르다.

**factory 가 못 이기는 기계적 이유 셋** (40평·중유동 기준):

1. **권리금 항 `prem/100` 이 세 tier 에 동일**하다 → `prem` 이 커질수록 invest 가
   수렴한다(26:15:9 → 146:135:129). 분모가 같아지면 "회수 최단"은 "순익 최대"와
   같은 말이 되고, 순익은 언제나 premium 이 최대다.
2. **net 격차(5.7:3.3:1)가 invest 격차(2.9:1.7:1)보다 크다** → `prem=0` 이라도 진다.
3. **비용에 매출비례항이 없어 매출이 곧 순익**이다.

factory 가 이기는 8건은 전부 `prem=0` · `rent ≤ 150만원` 으로, 실 인벤토리 최저
임대료(195만원) 밖이다. 즉 **현실에서는 도달 불가능**하다.

### 0-B. tier ↔ 업종 대표군 + 매출 실측 (2026-08-22 결정·산출)

원가율·인건비의 공개 통계는 전부 업종별로 공표되는데 우리 축은 전략(tier)이다.
그래서 **tier 를 업종 대표군으로 정의**했다(대안이던 "업종 무관 운영방식"은 외부
통계를 못 붙여 기각).

| tier | 업종 대표군 |
|---|---|
| premium 고급화 | 일식·양식·중식음식점 |
| value 가성비 | 한식음식점·분식·치킨·호프간이주점 |
| factory 공장제 | 커피-음료·패스트푸드·제과점 |

이 매핑으로 상권×업종 추정매출 ÷ 점포수 ÷ 3개월 → **점포당 월매출**을 실측했다
(`data/pipelines/build_posting_revenue.py`, 20261분기, 점포 5개 이상 상권만):

| tier | 관측 | 점포 | 중앙(만원/월) | p25~p75 |
|---|---|---|---|---|
| premium | 253 | 5,967 | **1,698** | 862~2,849 |
| value | 393 | 18,226 | **2,078** | 1,151~3,255 |
| factory | 264 | 7,035 | **1,317** | 554~2,411 |

🔴 **실측이 모델의 tier 서열을 뒤집는다.** 모델은 premium > value > factory
(40평·중유동에서 2,790 : 1,960 : 1,150)를 전제하는데 실측은 **value > premium >
factory** 다. 업종별로 보면 한식음식점 중앙 2,771 이 양식음식점 1,185 의 2.3배다 —
"고급화 = 고매출"이 서울 실측에서 성립하지 않는다(객단가는 높아도 회전이 낮다).

현행 계수를 실측 수준에 맞추는 배율은 **premium ×0.632 · value ×1.103 · factory
×1.192** 다. 즉 **현행 모델은 premium 매출을 58% 과대평가**하고 있었다.

⚠ 한계: 상권분석에 점포 면적이 없어 이 실측은 매출의 **수준**만 고정한다.
면적 **기울기**(`k`)는 여전히 근거가 없다.

### 0-C. `roi_basis` — 유령 필드였다 (해소)

`recommend_tier` docstring 이 "응답의 `roi_basis` 가 이 한계를 함께 내려보낸다"고
적고 있었으나, **저장소 전체에서 그 문자열은 그 한 문장뿐**이었다. `feb6630` 에서
docstring 한 줄로만 추가됐고 필드는 구현된 적이 없다 — 화면은 "회수 1.8개월"을
아무 경고 없이 보여주고 있었다. 08-22 에 실제 필드(`basis` · `viable` ·
`unviable_note`)로 구현했다.

### 0-D. 감도 실험 — 32조합 전수 (2026-08-22)

`scripts/posting_cost_sensitivity.py` 로 재현한다. 축 셋 × 판정 셋:

- **매출**: R0 현행계수 / R1 실측수준정렬(§0-B 배율)
- **원가**: C0 없음 / C1 균등33% / C2 차등38·33·28 / C3 차등32·35·40
- **인건비**: `월 215.7만원 × 필요인원`. 단가는 2026 최저임금(시급 10,320원 ×
  209시간, 고용노동부) 월 환산 — **4대보험 사업자부담 미포함**.
  L0 없음 / L1 3.0·2.0·1.0명 / L2 4.5·2.5·1.2명 / L3 면적비례(12·18·30평per인)

**통과 조건은 셋으로 늘렸다.** 기존 둘(마진 10~20% · factory 1위 발생)만으로는
"절반이 회수불가인데 남은 절반의 마진은 예쁜" 해가 통과한다. **회수불가 ≤20%** 를
셋째로 넣는다.

읽어야 할 결과 넷:

1. **R0(현행 매출계수)에서는 통과 조합이 0개다.** 마진을 10~20%로 내리면 회수불가가
   13~48%로 튄다. 즉 **비용만 고쳐서는 어떤 값을 넣어도 통과할 수 없다** —
   매출계수를 함께 고쳐야 한다.
2. **원가만 넣으면 순위가 안 바뀐다.** C1·L0 에서 premium 211승 / factory 0승.
   매출비례 비용은 세 tier 를 같은 비율로 깎아 **순서를 보존**한다. 순위를 만드는
   것은 **tier 간 차등**이지 원가 자체가 아니다.
3. **인건비가 순위의 지렛대다.** R0·C2·L2 에서 premium 1승 / value 115 / factory 23.
   차등 고정비라 저매출 tier 에 유리하게 작용한다.
4. **통과한 4조합은 전부 원가 또는 인건비 중 하나가 0이다.**

| 통과 조합 | 마진(P) | factory 승 | 회수불가 |
|---|---|---|---|
| R1 · C0 없음 · L1 | 12.5% | 19 | 0.4% |
| R1 · C0 없음 · L3 면적비례 | 13.3% | 7 | 1.1% |
| R1 · C1 균등33% · L0 없음 | 19.8% | 3 | 3.3% |
| R1 · C2 차등38/33/28 · L0 없음 | 14.8% | 23 | 3.3% |

🔴 **원가와 인건비를 둘 다 현실적으로 넣으면 통과 조합이 사라진다** — R1·C1·L1 은
premium 마진 −20.5%, 회수불가 21.5%. 두 가지 해석이 가능하고 아직 어느 쪽인지 모른다:

- (가) **사실이다.** 서울 주요 상권 임대료에서 소규모 외식 창업의 상당수는 실제로
  회수가 안 된다. 그렇다면 이건 버그가 아니라 이 제품이 내놓아야 할 **정보**다.
- (나) **기준이 틀렸다.** "마진 10~20%"는 살아남은 점포의 수치인데 모델은 평균적
  자리를 계산한다. 생존 편의(survivorship)를 비교하고 있는 것일 수 있다.

#### (가)/(나) 판별 — 08-22 추가 진단

R1·C1·L1(회수불가 58/270 = 21.5%)에서 **회수불가가 무작위가 아니라 집중돼 있다**:

| | 임대료 중앙 | 면적 중앙 | **평당 임대료** | **임대료/최대매출** |
|---|---|---|---|---|
| 회수 가능 (212건) | 505만원 | 36평 | 13.5만원 | 23.8% |
| 회수 불가 (58건) | 732만원 | 30평 | **23.5만원** | **41.5%** |

전체 270유닛 중 **200건(74%)이 임대료/매출 20% 초과**다(외식업 통상 건전선은
10~15%, 20%가 위험선).

**(가) 쪽 근거가 더 강하다.** 결정적인 것은 우리 인벤토리가 정의상 **공실**이라는
점이다 — 직전 임차인이 나간 자리이고, 나가는 가장 흔한 이유가 임대료 부담이다.
"공실 유닛의 임대료/매출 비율이 높다"는 것은 계산 오류가 아니라 **그 자리가 공실인
이유** 자체일 수 있다. 잘 되는 자리는 애초에 공실이 아니다(생존 편의의 거울상).

⚠ 다만 (가)로 확정하기 전에 확인할 것 하나: `rent` 는 R-ONE **상권 평균 임대료 ×
면적 × 층계수**로 만든 추정치이지 실제 계약가가 아니다. R-ONE 은 **중대형 상가**
기준이라 소규모 점포에 과대일 수 있고, 공실 호가는 실제 계약가보다 높은 경향이 있다.
이 편의를 재려면 실계약 임대료 표본이 필요하다.

또 하나: **R1 에서 premium 은 270건 중 1위가 0건**이다. 실측 서열이 value 우위라
그대로 반영된 결과인데, "고급화 전략이 서울 어디에서도 최선이 아니다"는 결론은
factory 0승과 똑같은 종류의 死문항이다. §0-B 의 업종 매핑을 다시 볼 여지가 있다.

### 0-F. KOSIS 실측 — 두 구멍이 모두 닫혔다 (2026-08-23)

`KOSIS_API_KEY` 발급 후 `scripts/kosis_probe.py` 로 실제 값까지 확인했다. 08-22 에
"열어 봐야 안다"고 남긴 두 질문에 답이 나왔고, **둘 다 기대보다 좋다.**

통계표: **`orgId=101` · `tblId=DT_3KB9001`** (서비스업조사 — 시도/산업별 총괄), 기준연도 **2024**.

**질문 1 — 음식점업을 어느 수준까지 세분하는가?** → **KSIC 5자리까지.** tier 대표군이
전부 개별 코드로 존재한다(산업분류 797건 중 5자리 477건):

| tier | 대표군 | KSIC |
|---|---|---|
| premium | 일식 · 양식 · 중식 | 56122 · 56123 · 56121 |
| value | 한식일반 · 치킨 · 생맥주 | 56111 · 56162 · 56213 |
| factory | 커피 · 패스트푸드 · 제과 | 56221 · 56161 · 56150 |

**질문 2 — 영업비용을 항목별로 주는가?** → **항목별로 준다.** 매출액(T03) ·
영업비용(T05) · 매출원가(T051) · 인건비(T052) · 임차료(T053) · 기타경비(T054) ·
영업이익(T06), 단위 백만원.

⚠ 단 **매출원가(T051)는 음식점업 전 업종 미공표(`-`)** 다. 대신 항등식이 정확히
성립한다(9개 업종 전부 잔차 ≤1백만원 = 반올림 오차):

```
영업비용 = 인건비 + 임차료 + 기타경비        # 매출원가는 기타경비에 흡수돼 있다
```

즉 **원가를 항목으로 분리하지는 못한다.** 그러나 비용 모델에 필요한 것은 원가율이
아니라 **영업비용률 전체**이므로 이걸로 충분하다 — 오히려 항목을 쪼개 합성할 때
생기는 가정이 없어진다.

### 0-G. 구현해 보니 막는 것은 비용이 아니었다 — 매출의 면적 기울기 (2026-08-23)

§0-F 는 "이제 막는 것은 자료가 아니라 구현"이라고 적었다. 구현했더니 **틀렸다.**
실측 비용을 정직하게 넣으면 통과가 아니라 붕괴가 나온다.

**산출물부터 고정했다.** §0-F 의 표는 문서에만 있었다 — 코드가 못 읽고, 낡아도
아무도 모른다. `data/pipelines/build_posting_cost_rates.py` 로 KOSIS 에서 받아
`gold/platform_posting_cost_rates.json` 으로 떨구고 추적 예외까지 걸었다.
9개 업종 전부 항등식(`영업비용 = 인건비 + 임차료 + 기타경비`) 잔차 ≤1백만원.

⚠ **임차료를 빼고 쓴다.** KOSIS 영업비용에는 임차료가 이미 들어 있는데 우리
`month_cost` 는 유닛별 임대료(R-ONE)를 따로 갖는다. 그대로 곱하면 이중계상이므로
파이프라인이 `opex_rate_ex_rent` 를 함께 낸다:

| tier | 영업비용률 | 임차료율 | **비임차 영업비용률** | 인건비율 |
|---|---:|---:|---:|---:|
| premium | 94.2% | 5.9% | **88.3%** | 18.0% |
| value | 93.0% | 5.2% | **87.9%** | 13.0% |
| factory | 91.2% | 4.3% | **87.0%** | 15.2% |

**결과 — `cost = rent + rev × 비임차비용률` 로 실 유닛 270건:**

| 매출축 | 임대료 | 회수불가 | 마진중앙 P/V/F |
|---|---|---:|---|
| R1 서울수준정렬 | 호가 그대로 | **96.3%** | −21.3 / −14.7 / −29.4 |
| R1 | −40% | 72.2% | −8.1 / −4.0 / −12.4 |
| R2 거점별정렬 | 호가 그대로 | **86.3%** | −27.5 / −14.5 / −28.7 |
| R2 | −40% | 59.3% | −11.8 / −3.9 / −12.0 |

통과 조건 셋(마진 10~20% · factory ≥1위 · 회수불가 ≤20%)과 자릿수가 다르다.
임대료를 40% 깎아도 안 된다 — §0-D 가 의심하던 "R-ONE 이 과대"로는 설명이 안 된다.
(그 의심 자체도 틀렸다: `build_posting_inputs.py` 가 쓰는 것은 중대형이 아니라
**소규모상가**(`rent_small`)이고, 단위 변환 `천원/㎡ × 평 × 3.3058 ÷ 10` 도 맞다.)

#### 원인 — 임대료는 면적에 비례하는데 매출은 아니다

| | 값 |
|---|---|
| 우리 유닛 임대료 / 거점실측매출 (중앙) | **32.8%** (p10 14.8 · p90 83.7) |
| KOSIS 실제 임차료율 | **4.3~5.9%** |

6배다. 원인은 `_revenue_factor()` 가 매출 **수준**을 *점포 하나*의 실측 중앙에
맞추는데, 그 점포가 우리 유닛보다 훨씬 작다는 것이다. KOSIS 점포당 임차료를
거점 평당임대료(중앙 19.3만원/평)로 나눠 평균 점포 면적의 **하한**을 잡으면:

| tier | 평균 점포 면적 ≥ | 우리 유닛(중앙 34평) 대비 |
|---|---:|---|
| premium | 12.6평 | **2.7배** |
| value | 7.1평 | **4.8배** |
| factory | 7.1평 | **4.8배** |

`rent` 는 면적에 비례해 커지는데(R-ONE × 면적 × 층계수) 정렬된 매출은 평균 점포
크기에 묶여 있다. 그래서 임대료/매출이 구조적으로 6배 부풀고, 정직한 비용률을
넣는 순간 전부 적자가 된다. **§0-B 가 "면적 기울기(k)는 근거가 없다"고 남긴 한계가
사소한 단서가 아니라 지배적 오차였다** — 회수불가를 3% 와 96% 사이에서 가른다.

#### 기울기는 지금 있는 자료로 못 정한다 (순환한다)

평당매출 = 점포매출 ÷ 평균면적, 평균면적 = 임차료 ÷ 평당임대료. 둘을 합치면
평당매출 = 평당임대료 ÷ (임차료/매출) 이라 **모든 유닛이 정의상 임대료비율
5.5% 에 고정**된다 — 마진이 전부 같아져 자리를 가리지 못한다. 점포 **면적** 자료가
따로 있어야 하고, 상권분석에는 없다. §0-E 의 공정위 가맹사업 정보공개서(기준면적)가
그 자료이고 아직 `ESSENTIAL_PARAMETER_ERROR` 로 막혀 있다.

#### 곁가지 소득 — R2 가 `factory 0승` 死문항을 푼다

`_revenue_factor()` 는 서울 전체 중앙 하나로 54거점을 맞춘다. 그런데 `rent` 는
거점별 실측이다 — **비싼 거점의 임대료에 서울 평균 매출을 짝지어** 놓고 있었다.
`platform_posting_revenue.json` 에는 거점별 값이 54/54 다 있었다.

| 축 | factory 1위 (C1·L0) |
|---|---:|
| R1 서울수준정렬 | 3 |
| **R2 거점별정렬** | **82** |

08-22 에 "factory 0승은 死문항"이라고 적은 것의 원인 하나가 이거였다. 다만 R2 도
면적 기울기는 못 고치므로 KOSIS 비용에서는 여전히 86% 회수불가다. **그래서 R2 를
서빙(`tier_scenarios`)에는 아직 넣지 않았다** — 기울기가 정해지면 매출 수준이
어차피 다시 움직여 두 번 보정하게 된다. 하네스에는 축으로 남겨 두었다.

#### 판단이 필요하다 (제품 결정)

비용 모델을 낡은 채로 두면 통과 조합이 있지만(R2·C1·L0 → 마진 12.9% · factory 82승 ·
회수불가 3.3%), 그건 **원가·인건비를 계속 빼 두어야만** 성립한다 — 이 게이트가
없애려던 바로 그것이다. 셋 중 하나를 골라야 한다:

1. **기울기를 실측한다** — 공정위 가맹정보 기준면적으로 평당매출을 세운다.
   엔드포인트 파라미터를 뚫어야 한다(못 얻는다 → 조사 필요).
2. **기울기를 가정으로 고정한다** — 서울 평균 평당매출을 기울기로 쓰고 거점별
   임대료 편차만 손익에 반영한다. 오늘 정하면 풀리지만 근거는 가정이다.
3. **인벤토리 정의를 바꾼다** — 34평 자리를 평균 점포 크기로 쪼개 여러 점포로 본다.
   공실 유닛의 의미 자체가 바뀐다.

재현: `python data/pipelines/build_posting_cost_rates.py` → `python scripts/posting_cost_sensitivity.py`

### 0-H. 옵션 2 배선 — 매출을 면적에 비례시켰다 (2026-08-23)

§0-G 가 남긴 세 선택지 중 **②(기울기를 미지수 하나로 줄여 외부 앵커에 고정)** 를 배선했다.
①(공정위 실측)은 엔드포인트가 막혀 있고, ③은 사실 기울기 문제가 아니었다.

#### 바뀐 식

```
이전  rev  = area × foot_k × r_a + r_f      # r_a = 41/30/18 — 손으로 적은 값
      cost = rent + area × c_a + c_f        # 원가·인건비 없음

지금  rev  = area × foot_k_norm × 평당매출[tier][거점]
      cost = rent + rev × 비임차_영업비용률[tier]        # KOSIS 서울 2024
      평당매출[tier][거점] = 거점별 실측 매출중앙 ÷ A[tier]
```

**핵심은 고정항(`r_f`)이 없어진 것이다.** 임대료는 면적에 비례하는데 매출은 안 그래서
임대료/매출이 6배 부풀어 있었고, 그게 회수불가 96%의 기계적 원인이었다. 미지수도
여섯(`r_a`·`r_f` 각 3)에서 **A 셋**으로 줄었다.

#### A 를 마진에 맞추지 않은 이유 — 그러면 검증이 순환한다

A 를 "마진 중앙이 KOSIS 영업이익률과 같아지도록" 고르면 **A=5.1평**이 나온다. 그런데
그건 한식집 평당 월매출 563만원(외식업 통상 200~400만원)을 뜻해 실물과 안 맞고,
무엇보다 **"KOSIS 마진이 재현된다"가 정의상 참**이 되어 아무것도 검증하지 못한다.

그래서 **임차료에서 독립 유도**한다:

```
A[tier] = (KOSIS 점포당 월 임차료) ÷ (거점 평당임대료 중앙 19.3만원/평)
        → premium 12.6평 · value 7.1평 · factory 7.1평
```

마진은 이 A 의 **결과**이지 입력이 아니다. 그래서 결과를 KOSIS 와 대조하는 것이
실제 검증이 된다.

| tier | 평당매출 중앙 | 마진 중앙(모델) | KOSIS 실측 영업이익률 |
|---|---:|---:|---:|
| premium | 141 만원/평 | **−1.2%** | 5.8% |
| value | 315 | **6.9%** | 7.0% |
| factory | 219 | **4.9%** | 8.8% |

**value 는 거의 정확히 맞고(6.9 vs 7.0), factory 도 대역 안이다.** 평당매출도 외식업
통상 대역(200~400)에 든다. 마진에 맞추지 않고 얻은 일치라 이건 대조로서 의미가 있다.

#### premium 이 대역 밖인 것은 버그가 아니다

premium 중앙 −1.2% 는 §0-B 실측과 **같은 방향**이다 — 서울에서 "고급화 = 고매출"이
성립하지 않아 tier 서열이 value > premium > factory 다(한식 중앙 2,771 vs 양식 1,185).
게다가 **A 는 하한**이다(분모로 쓴 평당임대료가 서울 전체가 아니라 프라임 54거점
값이라, 서울 평균이면 A 가 더 컸다). A 가 크면 평당매출이 낮아져 마진이 더 나빠지므로
premium 은 지금 값이 **낙관 쪽**이다.

#### 통과 조건 — 셋 중 둘. 그리고 기준 하나를 실측이 반증했다

| 조건 | 결과 | |
|---|---|---|
| factory 일부 1위 | **90승 / 270** | ✅ 死문항 해소 |
| 회수불가 ≤20% | **2.6%** | ✅ |
| 마진(P) 3.5~10.5% | premium −1.2% | ❌ (value·factory 는 통과) |

⚠ **마진 기준을 10~20% → 3.5~10.5% 로 내렸다.** 10~20% 는 KOSIS 를 얻기 전에 감으로
적은 값인데, 서울 2024 실측 영업이익률이 3.5~10.5% 다. 실측이 기준을 반증했으므로
기준을 실측 대역에 맞춘다 — 그대로 두면 **어떤 조합도 통과할 수 없고, 통과한다면
그건 비용을 덜 센 것**이다. 기준을 낮춰 통과시킨 것이 아니라 반대다(감도표에서
기존 통과 조합 4개가 이 변경으로 탈락했다).

#### 두 모델이 공존한다 — 폴백을 조용히 하지 않는다

거점에 실측 재료가 없으면 낡은 계수 모델로 폴백하되, 각 시나리오의 `basis` 가
어느 쪽이 돌았는지 밝힌다(`kosis-opex+measured-revenue` / `rent+fitout`).
현재 폴백은 **garak 1곳 5유닛**(premium 매출 표본 부족)뿐이다. `unviable_note` 도
실제로 돈 모델의 한계 문구를 붙인다 — 폴백으로 계산해 놓고 실측 모델의 한계를
적으면 그 자체가 거짓 근거다.

#### 감도표는 이제 서빙 코드를 **호출**한다

`scripts/posting_cost_sensitivity.py` 에 `_shipped()` 를 넣어
`districts.tier_scenarios` 를 실호출한다. 격자를 손으로 재현하면 반드시 원본과
어긋나는데(스크립트의 `SPEC` 상수가 이미 그 위험을 안고 있다), 배선이 끝난 모델은
재현하지 않고 부르므로 표가 프로덕션과 어긋날 수 없다.

검증: `tests/test_posting_revenue.py` 12건. `test_revenue_is_proportional_to_area`
(고정항 부활 방지) · `test_avg_store_pyeong_is_derived_from_rent_not_margin`
(A 유도식 고정) · `test_margins_land_in_kosis_band_for_value_and_factory`(순환하지 않는 대조).

#### 곁가지로 드러난 결함 — 카드의 `rec_top` 이 첫 유닛만 보고 있었다

회수불가가 실제로 생기자(7/270 = 2.6%) 거점 카드의 `rec_top` 이 빈 문자열로 떨어지는
경우가 나왔다. 원인은 `recs[0]` — **첫 유닛의 추천**을 그대로 쓰고 있었던 것이다.
첫 유닛이 회수불가면 나머지 넷이 멀쩡해도 카드가 조용히 빈다. `unviable_note` 가
유닛 상세에서 고쳤던 것과 **같은 실패 양식**이라 카드에서도 같게 고쳤다 —
가장 많이 추천된 전략을 쓰고, 세 전략 모두 불가인 거점에서만 빈다.

#### 회수불가는 어디에 몰리는가 — 이게 제품의 주장이다

| 거점 | 평당임대료 | 평당매출(value) | 임대료/매출 |
|---|---:|---:|---:|
| seochon | 30.5만 | 187만 | **16.3%** |
| myeongdong | 48.8만 | 340만 | **14.4%** |
| yeonnam | 18.7만 | 144만 | **13.0%** |
| … | | | |
| garak | 10.5만 | 826만 | 1.3% |

마진 ≈ 12% − 임대료/매출 이므로 13% 를 넘는 순간 음수가 된다. 회수불가 7건이
**yeonnam 4 · myeongdong 3** 에 몰린 것은 무작위가 아니라 그 구조다. "이 자리는
그 자리가 벌 수 있는 것에 비해 임대료가 높다" — 공실 인벤토리에서 우리가 보여주려던
바로 그 신호다.

#### 화면도 같이 닫았다 — §0-C 가 API 에서만 끝나 있었다

2026-08-22 에 `viable`·`basis`·`unviable_note` 를 **API 에** 만들었는데, 프론트는
그걸 타입에조차 갖고 있지 않았다. 카드는 회수불가를 `roi_months >= 99 ? "—"` 로만
표시했다 — **"모른다"와 "안 된다"가 같은 기호**였다. 비용 모델이 낙관적이라
회수불가가 거의 안 나와 잠복해 있던 결함이고, 실측 모델부터 실제로 뜬다.

- 회수 행: `viable` 이 거짓이면 **"회수 불가"** 라고 적는다(주황).
- 세 전략 모두 불가면 그 사실과 이유("임대료가 이 면적이 낼 수 있는 매출에 비해
  높다")를 카드에 띄운다. 숫자만 비워 두면 "데이터가 없다"로 읽힌다.
- **비용 기준 배지**를 카드에 붙였다(`KOSIS 실측비용` / `비용 일부 미반영`) —
  `basis` 가 화면에 도달하지 못하면 그 필드를 만든 의미가 없다.

#### 남은 것 → §0-I 에서 해소했다

A 를 공정위 기준면적으로 갈아끼우는 일(§0-E 옵션 1). 같은 날 오후에 했고, 그 과정에서
**분자 쪽 과소추정**이 함께 드러났다.

### 0-I. A 를 공정위 실측으로 갈았더니 분자가 드러났다 (2026-08-23 오후)

#### 면적은 나눗셈 하나로 나온다

공정위 API(`data.go.kr` 15110241 · 브랜드별 가맹점 현황)는 면적을 직접 주지 않지만
같은 행에 `avrgSlsAmt`(평균매출)와 `arUnitAvrgSlsAmt`(면적단위평균매출)를 준다.
정보공개서 표준양식의 면적단위가 **3.3㎡(1평)** 이므로

    A(평) = avrgSlsAmt / arUnitAvrgSlsAmt

이고, 둘이 같은 금액 단위라 **단위가 무엇이든 상쇄된다**. 기존 `DATA_GO_KR_SERVICE_KEY`
로 바로 붙었다(활용신청 이미 완료, totalCount 11,834 브랜드).
수집: `data/pipelines/build_posting_store_area.py` → `gold/platform_posting_store_area.json`.

가맹점수로 가중한 중앙값을 주값으로 쓴다 — 1개점 신생 브랜드와 1,000개점 브랜드를
같은 무게로 세면 소형 브랜드로 쏠린다(value 는 단순중앙 25.4 → 가중 18.5 로 움직인다).

| tier | 임차료 역산(오전) | **공정위 실측** | 브랜드 | 가맹점 |
|---|---|---|---|---|
| premium | 12.6평 | **20.8평** | 452 | 10,316 |
| value | 7.1평 | **18.5평** | 1,828 | 74,083 |
| factory | 7.1평 | **17.1평** | 536 | 37,143 |

**한식집 7.1평은 실물이 아니었다.** §0-H 가 A 를 하한이라고 적어 둔 것이 맞았고,
실제 격차는 2~3배였다.

#### A 만 키웠더니 모델이 무너졌다 — 범인은 분자였다

| A | 회수불가 | factory 1위 | 평당매출 중앙 |
|---|---|---|---|
| 임차료 역산 12.6/7.1/7.1 | 2.6% | 90 | 141 |
| 공정위 실측 20.8/18.5/17.1 | **50.0%** | 51 | **85~121** ← 상식대역 밖 |
| 유닛과 같은 척도 34/34/34 | 77.8% | 21 | — |

A 가 작을수록 모델이 좋아 보인다. 즉 **오전의 "회수불가 2.6%" 는 A 를 작게 잡아
매출을 3배 부풀린 결과였다.**

원인을 분자에서 찾았다. 분자는 서울 상권분석 추정매출 ÷ 점포수인데, KOSIS
서비스업조사(사업체 전수)와 대면 **1.2~2.3배 과소**다:

| tier | KOSIS 점포당(만원/월) | 상권분석 중앙 | 배율 | KOSIS ÷ 공정위 A |
|---|---|---|---|---|
| premium | 4,063 | 1,782 | 2.28 | **195** 만원/평 |
| value | 2,653 | 2,227 | 1.19 | **143** |
| factory | 3,391 | 1,531 | 2.21 | **198** |

공정위 면적과 KOSIS 매출은 **서로 독립인 두 실측**인데, 짝지으면 평당매출이 업계
통상(150~300만원/평·월)에 정확히 들어온다. 서로를 검증한 셈이라 이 조합을 채택했다.

#### 지금 식 — 세 실측이 각자 잘하는 축을 맡는다

    평당매출[tier][거점] = (상권분석[거점] ÷ 상권분석 서울중앙) × (KOSIS 점포당 ÷ A[tier])
                           └──── 거점 상대수준 ────┘             └──── 절대수준 앵커 ────┘

거점을 구분하는 소스는 상권분석뿐이므로 **비율로만** 쓰고, 절대 수준은 KOSIS 로
앵커한다. 거점 서열은 보존되고 수준만 제자리를 찾는다(테스트가 서열 보존을 고정한다).

#### 통과 조건 — 넷 중 셋

| 조건 | 결과 | |
|---|---|---|
| 회수불가 ≤20% | **10.0%** | ✅ |
| factory 일부 1위 | **165승 / 270** | ✅ |
| 평당매출 상식대역(100~600) | 195 / 144 / 201 | ✅ |
| 마진(중앙) 3.5~10.5% | 2.4 / 0.7 / 4.2 | ❌ **셋 다 대역 밖** |

#### 마진이 대역 밖인 것은 산술로 닫힌다 — 그래서 기준 쪽이 틀렸다

    마진 = (1 − 비임차비용률) − rent/rev
         = (KOSIS 이익률 + KOSIS 임차료율) − rent/rev        ← 항등식, 소수점까지 성립
         = KOSIS 이익률 − (rent/rev − KOSIS 임차료율)
                          └────── 프라임 프리미엄 ──────┘

| tier | 우리 rent/rev | KOSIS 임차료율 | 프라임 프리미엄 | 마진 중앙 | KOSIS 이익률 |
|---|---|---|---|---|---|
| premium | 9.5% | 5.9% | **3.5%p** | 2.4% | 5.8% |
| value | 11.7% | 5.2% | **6.6%p** | 0.7% | 7.0% |
| factory | 9.6% | 4.3% | **5.3%p** | 4.2% | 8.8% |

우리 유닛은 전부 프라임 54거점이라 매출 대비 임대료가 서울 평균보다 3.5~6.6%p 높고,
**딱 그만큼 마진이 깎인다.** 즉 "마진 중앙이 KOSIS 대역 안"은 프라임 인벤토리에
대면 애초에 틀린 기준이다 — 대역 안에 들면 오히려 프라임 자리를 서울 평균과 같은
자리에 놓는 셈이다.

그래서 **조건을 폐기하지 않고 ❌ 로 남긴 채**, 격차가 위 분해로 닫히는지를 넷째
조건으로 세워 ✅ 로 셌다(`test_margin_gap_is_exactly_the_prime_rent_premium`).
기준을 갈아 통과시킨 것으로 읽히지 않도록 둘 다 드러낸다.

#### 남은 것

- A 는 **전국 가맹점** 모집단이고 매출 분자는 서울이다. 축이 완전히 같지는 않다.
- 유닛 `area` 는 건축물대장 상업면적 ÷ capacity 라 중앙 34평인데 A 는 17~21평이다.
  두 면적 척도가 다른 것을 뜻할 수 있다 — capacity 추정을 의심할 자리다(Page 트랙).
- `area_basis`·`revenue_basis` 가 어느 모델이 돌았는지 진단에 드러낸다. 폴백은
  garak 1곳 5유닛뿐.

### 0-J. 실 인벤토리를 배선했다 — 화면이 시드 위에서 돌고 있었다 (2026-08-24)

`gold/{거점}/vacant_units.json` 은 08-22 에 54/54거점 **528유닛**으로 완주해 있었다.
그런데 `districts.resolved_units` 가 `DISTRICTS_BY_ID`(= 시드 `seoul_pages.DISTRICTS`,
**270유닛**)만 읽고 있어서, Posting API·화면이 계속 **손으로 적은 예시** 위에서 돌았다.
게이트는 "실제 공실 유닛 인벤토리 100%"로 켜져 있었고 그 문구도 *"배선을 막는 것은
이제 없다"* 라고 정확히 적혀 있었다 — 막을 것이 없다는 말은 **아직 안 했다**는 뜻이었다.
Program ①층이 08-23 에 겪은 것과 같은 실패 양식이다(수집이 아니라 배선).

#### 배선하면서 드러난 것 넷

**① 로더가 Program 안에만 있었다.** `program_site` 가 파일을 읽고 있었는데, 인벤토리는
Posting 의 산출물이고 Program 이 빌려 쓰는 것이다. 그대로 두면 Posting → Program 임포트로
의존 방향이 거꾸로 선다. `services/vacant_inventory` 로 내리고 양쪽이 같은 것을 본다 —
**파일 계약이 두 벌이 되면 한쪽만 고쳐지고 조용히 갈라진다.**

**② 실 인벤토리 유닛에는 `prem` 이 하나도 없다(528/528).** `tier_scenarios` 가
`unit["prem"]` 을 첨자로 읽던 동안에는 배선하는 순간 KeyError 였다. → §0-K.

**③ `rent` 도 없다 — R-ONE 으로 계산해 넣는 값이다.** 그래서 R-ONE 입력이 미적재인
환경(신규 클론)에서는 임대료가 빈 유닛이 나가고 계산이 죽는다. 인벤토리와 R-ONE 이
**함께** 있을 때만 실 인벤토리를 쓰고, 아니면 시드로 물러난다.

**④ 층이 전부 `1F` 다(528/528).** `build_vacant_units` 가 층을 1F 로 가정하기 때문이고,
`program_site.provenance` 가 이미 밝혀 둔 사실이다. 시드는 23%가 상층(계수 0.30~0.45)
이었으므로 **배선하면 임대료가 계통적으로 올라간다.** 이것이 아래 경제성 변화의 원인이다.

#### 경제성 — 시드 기준 §0-I 수치는 실 인벤토리에서 다시 재야 한다

| | 시드 270유닛 (§0-I) | **실 인벤토리 528유닛** |
|---|---|---|
| 회수불가 | 10.0% | **13.6%** |
| factory 1위 | 165 / 270 (61.1%) | **314 / 528 (59.5%)** |
| 마진 중앙 premium | 2.4% | **0.4%** |
| 마진 중앙 value | 0.7% | **−1.7%** |
| 마진 중앙 factory | 4.2% | **2.1%** |

**value 중앙이 0 을 넘어 내려갔다.** 종전 트립와이어는 `0 < 마진` 이었고 *"음수로
무너지면 그때는 모델을 의심한다"* 고 적혀 있었다. 울린 이유를 먼저 확인했고 **모델
고장이 아니었다** — §0-I 의 분해식 검증
(`test_margin_gap_is_exactly_the_prime_rent_premium`, 마진 = KOSIS 이익률 − 프라임
임대료 프리미엄)이 **그대로 통과한다**. 값이 내려간 것이지 설명이 깨진 것이 아니고,
원인은 위 ④(1F 가정)다. 그래서 트립와이어를 폐기하지 않고 하한만 0 → **−5%** 로
내렸다. 분해로 설명되는 폭을 넘어 무너지면(−10% 등) 그때는 정말 모델을 의심한다.

⚠ **남은 것**: 층 1F 가정이 풀리기 전까지 실 인벤토리의 임대료는 **상한**이다.
`area` 유닛 서열도 균등분할이라(대장 상업면적÷capacity) 같은 성격의 근사다.

### 0-K. `prem`(권리금)은 수집 과제가 아니라 입력 계약이다 (2026-08-24 결정 · 막힘 7)

게이트가 오래 `prem 0/54 ⬜(표본 밀도 부족)` 로 적혀 있었다. 실제로는 표본이 부족한
것이 아니라 **모집단이 없다** — 권리금은 공개 통계가 없고(bronze 전수 확인), 실제로도
임대인·기존 임차인과의 **협상값**이라 그 자리에 들어갈 기업만 안다. Program 입력 계약
③층(창업계획)이 *"아직 없는 가게의 강점은 어떤 데이터에도 없어서 기업이 넣는다"* 로
닫은 것과 **정확히 같은 성격**이다.

#### 정하기 전에 잰 감도 (시드 270유닛 전수)

| 측정 | 값 |
|---|---|
| `prem`→0 일 때 **추천(rec) 뒤집힘** | **14 / 270 (5.2%)** |
| **회수가부(viable) 변화** | **0 / 270** |
| `roi_months` 절대변화 | 중앙 **1.6개월** · p90 15.5 · 최대 58.2 |
| 시드 `prem` 분포 | 0인 유닛 88/270 · 나머지 중앙 1,550만원 · 최대 1.2억 |

무시할 수 없지만(추천 5.2% 를 바꾼다) **제품의 핵심 판정인 회수 가능/불가는 전혀
안 건드린다.** 즉 §0-I 의 "회수불가 10.0%" 결론은 `prem` 과 무관하게 성립한다.

#### 결정

`POST /ai/simulate-revenue` 의 `prem`(만원)으로 **기업이 넣는다.** 안 주면 0 을 전제로
계산하고 `inputs_source["prem"]` 이 `"absent"`(전제) / `"contract"`(받았다)로 어느
쪽인지 밝힌다. 음수는 0 으로 눕힌다 — 이 경로의 계약은 어떤 입력에도 같은 스키마를
돌려주는 것이다.

게이트에서는 **입력 4종의 분모에서 빼고**(수집으로 채울 수 있는 것은 셋이다) `prem` 은
'입력 계약' 항목으로 옮긴다. 근거 없는 0/54 를 계속 세면 "언젠가 수집하면 된다"로
읽히는데, **수집으로는 영영 안 채워진다.**

⚠ 지어내지 않은 것: 실 인벤토리 유닛의 `rec`·`persona`·`note`(시드 서술 문구)도 비운
채로 내보낸다. `rec` 은 이미 계산으로 대체됐고(`recommend_tier`), 나머지 둘은 근거 없이
적은 문구라 **실측 자리에 얹으면 실측처럼 읽힌다.** 스키마에서 선택 필드가 됐다.

### 0-L. 층 1F 가정을 걷어냈다 — 비용 모델 게이트 재수립 (2026-08-25)

§0-J ④가 남긴 것을 풀었다. 실 인벤토리 528유닛이 **전부 `1F`** 였고, 그것이 §0-I 의
통과 조건을 시드 기준으로 되돌려 세워야 하는 이유였다.

#### 1F 가정은 96.2% 에서 틀렸다

#### 새 가정을 들이지 않았다 — 이미 쓰던 면적을 쪼갰을 뿐이다

층별 면적은 `bronze/{거점}/*/bldg_flr_raw.json`(층별개요 원본)에 이미 있었다. 붙이기

#### ⚠ 넷 다 통과했다고 닫힌 것이 아니다

숫자가 원하는 방향으로 움직였을 때가 가장 위험하다. 마진이 대역 안에 든 **대가**를
같이 본다:

| factory | 6.1% | 4.3% | 1.8%p (5.3%p) | 7.0% |

premium 의 프라임 프리미엄이 **0.3%p** 다 — 프라임 54거점 인벤토리가 서울 **평균**과
같은 임대료 부담을 진다는 뜻이라, 이것대로 미심쩍다. §0-I 가 *"대역 안에 들면 오히려
이상하다"* 고 적었던 그 지점이다.

**두 모델은 참값을 사이에 두고 있다.**

- **1F 고정 = 상한.** R-ONE 소규모상가 임대료가 사실상 1층 기준이라 계수 1.00 이
  전 유닛에 걸린다.
- **층 면적 가중평균 = 하한에 가깝다.** 실제 창업 임차인은 저층으로 쏠리는데, 이
  모델은 건물의 모든 상업층을 면적 비중대로 평균낸다.

참값을 안다고 주장하지 않고 **괄호가 있다는 사실만 고정한다** —
`test_weighted_floor_rent_is_a_lower_bound_than_1f` 가 가중계수 < 1F 를 전수 단언하고,
`inputs_source["floor"]` 가 `flr_ouln`(실측 분포) / `assumed_1f`(폴백) 중 어느 쪽이
돌았는지 밝힌다. 임대료 **출처**(`inputs_source["rent"] == "rone"`)와는 다른 축이라
따로 둔다 — 한 라벨에 뭉치면 상한과 하한이 같은 이름으로 나간다.

#### 곁가지로 드러난 것 — 층 라벨과 임대료가 분리됐다

처음에는 대표 층을 **면적 최대 층**으로 골랐다. 그러자
`test_rent_falls_with_floor` 가 *"myeongdong 2F 평당 26.7 >= 1F 24.0"* 으로 걸렸다.
라벨은 최빈층인데 임대료는 가중평균이라 둘이 분리된 것이고, 버그가 아니라 **이 유닛이
특정 한 층이 아니라는 뜻**이었다. 라벨을 범위(`"1~5F"`)로 바꿨다 — 한 층을 적으면
"그 층의 자리"로 읽히는데 그건 우리가 관측한 것이 아니다. 테스트도 모델이 실제로
주장하는 것(상층 비중이 클수록 계수가 낮다)을 검사하도록 고쳤다.

#### 남은 것

**공실 유닛이 실제로 어느 층인지**(상가정보 `flrNo` 매칭)를 붙이면 괄호가 한 점으로
좁혀진다. 그 전까지 이 게이트의 ✅ 는 "하한에서 통과"라는 뜻이다.

### 0-M. 층 축을 끝까지 밀어 봤다 — 괄호가 좁혀진 게 아니라 **바닥을 쳤다** (2026-08-25 오후)

§0-L 이 "남은 것"으로 지목한 레버를 실행했다: **공실 유닛이 실제로 어느 층인가**.
결과는 예고와 달랐다. 괄호가 한 점으로 좁혀지지 않았고, 대신 **아래로 한 칸 더 내려간
순간 프라임 프리미엄이 부호를 넘어** 저장소의 트립와이어가 걸렸다. 그래서 싣는 값은
**되돌렸다.**

#### 새 자료를 받지 않았다 — 이미 있었다

§0-L 은 이 작업을 "상가정보 `flrNo` 매칭"이라 적어 두었고, 그래서 **수집 과제로**
읽혔다. 아니었다. Page 마스터(`build_page_master._aggregate`)가 같은 것을 이미 계산해
싣고 있다:

| 필드 | 뜻 |
|---|---|
| `com_floors` | 분모 — 건물의 상업 용도 층 |
| `occ_floors` | 분자 하한 — 상가정보 `flrNo` · 인허가 주소로 **점유가 확인된** 층 |
| `unknown_n` | 층 미상 점포로 배정된 층 수 (= 상한 − 하한) |

즉 수집이 아니라 **배선** 문제였다 — 이 저장소가 §0-J(시드 위에서 돌던 화면)에서
막 잡아 낸 것과 **같은 양식**이고, 그 직후 작성한 문서가 다시 같은 모양으로 적혀
있었다. "무엇을 받아야 하나"로 적기 전에 **이미 산출물에 있는지 먼저 세는 것**이
이 양식을 끊는 방법이다.

#### 배선 전 전수 프로브 (528유닛)

| 확인 항목 | 실측 |
|---|---|
| 공실 유닛 PNU 에 상가정보 점포가 있는가 | **528/528** (100%) |
| 그중 `flrNo` 값이 찍힌 점포가 있는가 | 365/528 (69.1%) |
| `floor_mix` 층이 `com_floors` 안에 있는가 | **528/528 일치** (벗어남 0) |
| 상업층이 전부 점유로 확인된 유닛 | **0** (좁히면 빈 집합이 되는 경우 없음) |
| 점유 층을 실제로 덜어낸 유닛 | **326/528** (나머지 202 는 `occ_floors` 가 비어 종전과 동일) |

세 번째가 §0-L 의 셋째 확인과 같은 성격이다 — 층 집합이 갈라지면 임대료가 분모와
다른 건물을 가리킨다.

#### 괄호의 네 끝 — 계수 중앙 (528유닛)

층 미상 점포(`flrNo` 공란 약 30%)가 괄호를 만든다. 층 미상을 **낮은 층부터** 점유로
앉히는 것은 `_aggregate` 의 상한 계산과 같은 규칙이다 — 규칙이 갈라지면 같은 건물에
대해 Page 와 Posting 이 서로 다른 층을 비었다고 말하게 된다.

| 모델 | 계수 중앙 | 회수불가 | 마진 중앙 P/V/F | **premium 프라임 프리미엄** |
|---|---|---|---|---|
| 1F 고정 (§0-J) | 1.000 | 13.6% | 0.4 / −1.7 / 2.1 | +5.3%p |
| 건물 전체 층 (§0-L · **싣는 값**) | 0.549 | 1.3% | 5.5 / 4.3 / 7.0 | **+0.3%p** |
| 빈 층 · 점유하한 (`vac_floor_mix`) | 0.487 | 1.1% | 6.0 / 5.2 / 7.6 | **−0.2%p** ⛔ |
| 빈 층 · 점유상한 (`vac_floor_mix_lo`) | 0.401 | 0.9% | 6.7 / 6.0 / 8.4 | −1.0%p ⛔ |

#### ⛔ 왜 안 실었나 — 통과 조건 넷은 **더 좋아졌는데** 트립와이어가 걸렸다

빈 층 모델은 통과 조건 네 개를 전부 유지하고 오히려 개선한다(회수불가 1.3 → 1.1%,
factory 417 → 419승, 마진이 KOSIS 대역 한가운데로). **그 넷만 봤으면 실었을 것이다.**

걸린 것은 게이트가 아니라 `test_margin_gap_is_exactly_the_prime_rent_premium` 의
단언이다:

```
premium: 프라임인데 임대료 비중이 서울 평균 이하 — 의심
assert -0.23089792926516417 > 0
```

우리 유닛은 전부 프라임 54거점이다. 그 인벤토리의 매출 대비 임대료가 서울 **평균보다
낮다**는 것은 물리적으로 성립하지 않는다. 임계값을 내려 통과시키는 것은 §0-I 가
금지해 둔 방향("기준을 갈아 통과시킨 것으로 읽히지 않도록")이라, **싣는 값을
`floor_mix` 로 되돌렸다.**

`vac_floor_mix` · `vac_floor_mix_lo` · `occ_floors` · `unknown_n` 은 산출물에 **남긴다** —
지우면 다음 사람이 같은 것을 다시 만든다(§0-J 이웃 피처와 같은 처리). 다만
`floor_basis` 는 **승격하지 않는다**: 라벨이 측정치 쪽으로 올라가면 응답이 "빈 층으로
계산했다"고 말하는데 실제로는 `floor_mix` 로 계산한다.

#### 그래서 무엇을 알게 됐나 — **층 축은 다 썼다**

프라임 프리미엄을 층으로 두 번 고쳤다: **+5.3 → +0.3 → −0.2%p.** 두 번째 수정은
5%p 를 움직였는데 세 번째는 0.5%p 를 움직이며 부호만 넘겼다. 즉 premium 티어의
프리미엄이 0 에 눌려 있는 것은 **층이 원인이 아니다.** value(+2.7 → +1.7)·
factory(+1.8 → +1.2)는 여전히 양수라 티어 사이의 차이도 층으로는 설명되지 않는다.

남은 후보는 **매출 절대수준의 프라임 보정**이다. 지금 매출은 KOSIS 서울 **평균**
점포당 매출에 앵커돼 있고(`revenue_basis = "kosis-anchored"`), 거점 격차는 상권분석
**비율로만** 들어간다(§0-I). 프라임 거점의 절대 매출이 서울 평균보다 높다면 분모가
과소평가돼 `rent/rev` 가 실제보다 **크게** 나와야 하는데, 관측은 반대 방향이다 —
이 어긋남이 다음에 풀 것이고, 층이 아니라 **분모**에 있다.

#### 고정한 것

- `test_vacant_floor_band_is_ordered` — 괄호가 뒤집히지 않는다(1F ≥ 전체 층 ≥ 빈 층 ≥
  하단). 지상 상업층 계수가 단조 감소(1F 1.00 · 2F 0.45 · 3F 0.40 · 4F+ 0.30)라
  성립하는 성질이고, 같은 테스트가 **싣는 계수가 `floor_mix` 인 것**과
  `inputs_source["floor"] == "flr_ouln"` 까지 전수 단언한다.
- `test_margin_gap_is_exactly_the_prime_rent_premium` — 임계값을 그대로 둔다. 이번에
  실제로 울려서 배선을 되돌린 트립와이어다.

### 0-N. 매출 앵커에서 버그를 하나 찾았고, 그런데 **가설은 기각됐다** (2026-08-25 저녁)

§0-M 이 다음 레버로 지목한 것을 실행했다: **매출 절대수준의 프라임 보정.** 버그는
실제로 있었고 고쳤다. 그런데 고치자 프라임 프리미엄이 **더 내려갔다** — 즉 §0-M 이
세운 가설은 틀렸다. 남은 불균형은 매출이 아니라 **임대료 쪽 층 기준**에 있다.

#### 찾은 버그 — "서울 중앙"이 우리 54거점의 중앙이었다

`per_pyeong()` 의 식은 이렇게 적혀 있다:

    평당매출 = (상권분석[거점] ÷ 상권분석 **서울중앙**) × (KOSIS 점포당 ÷ 공정위 A)

그런데 `_trdar_seoul_median()` 이 도는 대상은 `_revenue()` 이고, 이것은 산출물의
`districts` 키 — 즉 **우리 54거점**이다. 54개의 중앙을 "서울 중앙"이라 부르고 있었다.

결과가 결정적이다. 거점 배율 `m["median"] / seoul` 의 **중앙이 정의상 정확히 1.00**
이 된다. 프라임 인벤토리가 서울 평균보다 장사가 잘 되는지 여부가 **구조적으로
지워진다** — 매출 프리미엄은 0 으로 눌리고 임대료 프리미엄만 남는다. §0-L 이
*"프라임 54거점이 서울 평균과 같은 임대료 부담을 진다"* 며 미심쩍어한 그 모양의
절반이 여기서 나왔다.

제대로 된 기준점은 **같은 파일에 이미 있었다.** `build_posting_revenue` 가 서울 전체
상권을 `seoul` 키로 떨군다(관측 **393** · 점포 **18,226**). 서빙이 읽지 않고 있었을
뿐이다 — 산출물에 있는 값을 제품이 안 쓰는 것, §0-J·§0-M 과 **세 번째로 같은 양식**이다.

#### ⛔ 그런데 가설은 기각됐다 — 프리미엄이 **더** 내려갔다

§0-M 은 *"프라임 거점의 절대 매출이 서울 평균보다 높다면 분모가 과소평가돼
`rent/rev` 가 실제보다 크게 나와야 한다"* 고 적었다. 방향이 반대였다. 배율이 1.00 →
1.05 로 오르면 분모가 커지고 `rent/rev` 는 **작아진다**:

    premium 프라임 프리미엄   +0.29%p  →  **+0.0185%p**

트립와이어(`> 0`)를 통과하기는 하지만 **0.02%p 차이**다. 통과가 아니라 경계 위에
얹혀 있는 것이다. 즉 매출 앵커는 이 이상현상의 원인이 **아니었고**, 오히려 그것을
가리고 있었다.

#### 원인은 어디인가 — **층 기준이 비대칭이다**

프리미엄을 두 배율로 분해하면 자리가 정확히 드러난다. 항등식은
`프리미엄 > 0 ⟺ 임대료배율 > 매출배율` 이다(A 가 양변에서 약분된다).

서울 기준점은 KOSIS 에서 역산한다 — 점포당매출 × 임차료율 ÷ A:

| tier | 서울 평당임차료 | 우리 임대료배율(전체 층) | 매출배율 | 프리미엄 |
|---|---|---|---|---|
| premium | 11.58만원/평 | **0.96** | 1.05 | +0.02%p |
| value | 7.41만원/평 | 1.49 | 1.07 | +2.17%p |
| factory | 8.45만원/평 | 1.30 | 1.16 | +0.95%p |

premium 의 임대료배율이 **0.96** — 프라임 거점 유닛이 서울 평균 음식점보다 평당
임대료를 **덜** 낸다는 뜻이다. 여기가 남은 자리다.

**왜 그렇게 나오나.** 우리는 R-ONE(사실상 **1층 기준** 벤치마크)에 층 계수를 곱하는데,
그 계수를 **층별 면적 비중**(`floor_mix`, 중앙 0.549)으로 매긴다. 반면 KOSIS 임차료는
**점포가 실제로 있는 층**에서 지불된 금액이다. 두 층 기준이 다르다.

54거점 상가정보 **137,880개 점포**의 실측 층 분포로 재 보면:

    1F 42.9% · 2F 18.9% · 3F 11.9% · 4F 7.8% · 5F 5.7% · 6F+ 12.8%
    → 계수 가중평균 ≈ 0.63   (면적 비중 기준 0.549 보다 높다)

같은 건물 안에서 직접 비교하면 **점포 실분포 기준이 면적 비중 기준의 1.62배**다
(327동 중앙). 상업 면적은 상층에 넓게 깔리는데 점포는 저층에 몰리므로, 면적으로
가중하면 계통적으로 낮게 나온다.

즉 §0-M 이 "층 축은 다 썼다"고 적은 것은 **절반만 맞다.** 어느 층이 비었는지는
다 썼지만, **층 계수를 무엇으로 가중하는가**는 아직 안 건드렸다.

#### 다음 레버 — R-ONE 서울 평균

지금 서울 평당임대료 기준점은 KOSIS 역산 하나뿐이고, 거기에는 층 기준이 **섞여
있다**. 우리 쪽(R-ONE × 층 계수)과 같은 기준으로 맞추려면 **R-ONE 소규모상가의
서울 평균**이 필요하다. `data/collectors/rone_rent.py` 는 지금 우리 54거점만
필터해 받는데(`rone_cls` 가 `서울>도심>광화문` 형태의 계층을 들고 있다), 상위
계층 행을 같이 받으면 된다 — **수집 한 번**이면 두 기준을 같은 축에 놓을 수 있다.

그때까지 트립와이어의 `> 0` 은 **경계 위 통과**로 읽을 것. 임계값은 건드리지 않았다.

## 3. 작업 순서

> **현재 위치: 0번이 다음이다.** 1번은 외부 명세가 없어 막혀 있고, 그 사이 폴백의
> 입력(`rent`)과 기준(`rec`)을 올렸다. 이제 그 둘이 올라탄 **계산식**이 남았다.

0. **3-Tier 비용 모델 보정 (최우선)** — `month_cost` 에 원가·인건비를 넣는다.
   통과 조건 **셋**(§0-D): 마진 10~20% · `factory` 일부 조합 1위 · **회수불가 ≤20%**.
   **2026-08-23: 자료 구멍이 둘 다 닫혔다(§0-F).** 원가율은 KOSIS 서비스업조사
   `DT_3KB9001` 의 영업비용률(서울 2024, 업종별 89.5~96.5%)로 대체하고, 필요인원은
   인건비를 매출 대비 비율로 직접 얻으므로 **질문 자체가 없어졌다.**
   이제 막는 것은 자료가 아니라 **구현**이다. 남은 작업:
   - `tier_scenarios` 의 `month_cost` 를 매출비례 영업비용률로 재정의 → `COST_BASIS` 갱신
   - 매출계수 41/30/18 을 §0-B 실측(premium ×0.632 · value ×1.103 · factory ×1.192)으로 이동
   - 32조합 감도표(`scripts/posting_cost_sensitivity.py`) 재실행으로 통과 조건 셋 확인
   §0-D-1 대로 **비용만 고쳐서는 통과가 불가능**하다 — 둘을 같이 옮겨야 한다. §0-F 의
   실측이 이를 다시 뒷받침한다(업종 간 비용률 차이가 7%p 뿐이라 tier 를 가르는 것은
   비용이 아니라 매출이다).
1. **어댑터 계약 확정** — 외부 코파일럿의 입출력 명세 확보 → `services/posting.py`의 `_call_copilot()` TODO 해소. 그 전까지는 요청/응답을 `PostingRequest`/`PostingResult`로 고정해 둔다.
2. **폴백 유지** — `POSTING_COPILOT_URL` 미설정 또는 호출 실패 시 3-Tier 계산으로 동일 스키마 반환 (`source: "fallback-3tier"` 표기).
3. **정규화 검증** — 코파일럿 응답 필드 ↔ `PostingResult` 매핑 테이블 작성, 단위(만원/월) 불일치 방지.
4. **추천 연계** — GNN 업종 추천(Platform) 결과를 코파일럿 입력(업종 후보)으로 전달해 "이 공실 + 추천 업종 + 전략별 ROI"를 묶어 제공.
5. **근거 데이터 보강(선택)** — 공정위 가맹정보(창업비용, `api-keys-and-specs.md` §8-C)로 폴백 가정을 실데이터로 치환.
