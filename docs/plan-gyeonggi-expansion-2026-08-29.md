# 고양·파주 확장 기획 — 서울 스택이 어디까지 그대로 가고, 어디서 갈리나 (2026-08-29)

> **후속:** 경기 **20거점 등록·7거점 서빙**, 정본은 `docs/finding-goyang-paju-hubs-2026-08-30.md`.

## 0. 판정

**간다. 다만 서울 스택의 절반만 그대로 간다.**

| 트랙 | 판정 | 근거 |
|---|---|---|
| **Page**(공실 히트맵·3D) | ⭕ **거의 그대로** | 분자(상가정보)·분모(건축HUB)·폴리곤(V-World) 전부 전국 서비스. 이 세션에서 4개 지점 실측 프로브 통과 |
| **Platform**(정체성·업종 추천) | ◐ **절반** | 업종 구성·블로그·검색 트렌드는 전국. **"누가·언제 오나"는 서울 전용 소스라 교체** |
| **Posting**(3-Tier) | ◐ **조건부** | R-ONE 경기 표본이 **고양 2·파주 1** 뿐. 거점 수 상한이 여기서 정해진다 |
| **Program**(마케팅) | ◐ **절반** | 콘텐츠 생성은 전국. 행사는 서울열린데이터 전용이라 시 단위 소스로 교체 |

가장 큰 제약은 데이터가 없는 것이 아니라 **두 가지 구조**다 — R-ONE 표본 3곳(§3-A)과
계획상가(집합건물) 밀집(§3-B). 둘 다 아래에서 실측으로 짚는다.

⚠ **`archive/goyang-legacy/` 부활이 아니다.** 그건 2026-07-18 에 버린 정적 프로토타입
(CityDashboard/DistrictPPPP)이고 재도입 금지는 그대로다. 여기서 하는 것은 **현재 파이프라인에
도시 차원을 넣는 것**이다. 옛 모듈·옛 산출물은 참조하지 않는다.

## 1. 실측 프로브 — 되는지 먼저 쟀다

문서로 판단하지 않고 실제 API 를 4개 지점에 쏘았다(2026-08-29).

### 1-A. 소상공인 상가정보 (Page 분자) — ✅ 전 지점 정상

| 프로브 지점 | 점포 | 건물(bdMgtSn 그룹) | 건물당 점포 |
|---|---|---|---|
| 고양 일산 라페스타 | 4,118 | 110 | **37.4** |
| 고양 화정 | 2,873 | 340 | 8.5 |
| 파주 금촌 | 2,509 | 831 | 3.0 |
| 파주 운정 | 738 | 140 | 5.3 |
| (대조) 서울 가로수길 | 3,354 | 840 | 4.0 |

`bldMngNo` 누락은 0~5건으로 서울과 같은 수준이다. **건물당 점포 수는 §3-B 에서 다시 본다 —
이 표의 37.4 가 이번 확장의 최대 위험 신호다.**

### 1-B. V-World 건물 폴리곤 (Page 지도) — ✅ 정상
반경 400m bbox 1콜: 일산 라페스타 **171동**, 파주 운정 **568동**. 서울과 같은 경로.

### 1-C. 건축HUB 대장 (Page 분모) — ✅ 코드 변경 불필요
`page_hubs.py` 가 이미 적어 두었다: *"신규 거점을 추가할 때 필요한 것은 중심좌표와 반경뿐"* —
시군구·법정동은 점포·폴리곤의 PNU 19자리에서 건별로 파생한다. 서울 가정이 코드에 없다.
**병목은 코드가 아니라 일일 쿼터**다(§5 견적).

### 1-D. R-ONE 임대료·공실률 (Posting·LSTM) — ⭕ 있다, 3곳뿐

임대료 통계표(`T248223134698125`) 전량을 받아 세었다: 전국 **276개 표본 상권**, 그중 **경기 35곳**.
고양·파주에 걸리는 것은 셋이다.

| R-ONE 상권 | 지역 | vac_small | vac_mid | rent_small |
|---|---|---|---|---|
| `경기>고양시청` | 고양 덕양 | 22분기 | 22분기 | ✅ |
| `경기>탄현역` | 고양 일산서 | 22분기 | 22분기 | ✅ |
| `경기>파주시청` | 파주 금촌 | 22분기 | 22분기 | ✅ |

**22분기는 서울 거점(21분기)보다 길다** — LSTM 이력 요건은 오히려 여유가 있다.
없는 것: **일산 라페스타·웨스턴돔·운정신도시 표본**. 경기 35곳 목록에 일산·운정이라는
이름 자체가 없다.

## 3. 구조적 제약 둘 — 여기서 계획이 갈린다

### 3-A. R-ONE 표본이 3곳이라 "거점마다 임대 시계열"이 성립하지 않는다

서울 54거점은 **R-ONE 21분기 정확 매핑 표본을 전부 소진**하는 방식으로 뽑았다
(`seoul_pages.py` 헤더). 경기는 그 기준으로 세면 **고양 2 · 파주 1** 이 상한이다.

거점을 그보다 많이 넣으면 `rone_districts.py` 가 이미 경고한 상태가 된다 —
*"같은 R-ONE 상권을 공유하는 거점끼리는 해당 피처가 동일하다(거점 원핫으로만 구분됨)."*
서울에서도 공유 매핑이 8쌍 있지만, 경기는 **거의 전부가 공유**가 된다.

**그래서 두 갈래 중 하나를 골라야 한다.**

| 안 | 거점 수 | 대가 |
|---|---|---|
| **A. 표본 준수** | 고양 2 · 파주 1 (총 3) | 일산 라페스타·웨스턴돔·운정을 못 넣는다 — 상업적으로 가장 중요한 상권이 빠진다 |
| **B. 공유 매핑** | 고양 4~6 · 파주 2~3 | 임대료·공실 피처가 거점 간 동일. LSTM 은 사실상 3개 계열을 학습한다. **화면에 그 사실을 밝혀야 한다**(`rone_shared` 배지) |

**권고: B + 명시.** 서울에서 이미 확립한 원칙(합성값을 실측처럼 보이지 않게 한다)을
그대로 적용해, 공유 매핑 거점에는 `vacancy_source` 옆에 **"임대 앵커 공유"** 표기를 단다.
Posting 카드의 `inputs_source.rent` 도 `rone` 이 아니라 `rone-shared` 로 갈라 낸다.

### 3-B. 계획상가(집합건물) 밀집 — 우리 공실 계산이 가장 약한 지형이다

일산 라페스타는 **건물당 점포 37.4개**다. 서울 가로수길(4.0)의 9배이고, 이건 그 지역이
장사가 잘 된다는 뜻이 아니라 **점포가 집합상가 안에 들어 있다**는 뜻이다.

우리 공실률은 `_COUNTED_METHODS={'floor_ouln'}` 로 **일반건축물만** 분모에 싣는다.
집합건물을 넣으면 상가정보가 집합상가 내부 점포를 그 건물 `bdMgtSn` 으로 못 귀속시켜
공실률이 78~86% 로 튄다 — 서울에서 이미 정량 조사 후 **기각**했다(feature-posting §0-R,
`reports/expos_pip_recovery_probe_2026-08-26.json`). 검증할 R-ONE 집합상가 앵커도 없다.

즉 **일산 라페스타를 거점으로 넣으면 대다수 점포가 분모 밖으로 빠진다.** 서울에서 풀지
못한 문제를 고양에서 처음 만나는 것이 아니라, **고양이 그 문제의 정중앙**이다.

**그래서 거점 선정 기준에 한 줄이 추가된다:**
> 건물당 점포 수(상가정보 ÷ bdMgtSn 그룹)가 **10을 넘으면 후보에서 내리거나, 집합상가
> 비중을 명시한 채로 넣는다.** 프로브 4곳 중 화정(8.5)·운정(5.3)·금촌(3.0)은 통과,
> 일산 라페스타(37.4)는 걸린다.

Phase 1 착수 전에 후보 지점마다 이 비율을 재는 것이 **가장 싼 검증**이다(1콜 × 지점 수).

## 4. 폴더·코드 구조 — 복사가 아니라 도시 차원을 넣는다

### 4-A. 이미 도시 무관한 것 (건드리지 않는다)
```
data/bronze/{거점slug}/{날짜}/...     거점 단위 — 그대로
data/gold/{거점slug}/...              거점 단위 — 그대로
```
`page_hubs.PageHub` 는 slug·표시명·중심좌표·반경뿐이라 도시 가정이 없다.

### 4-B. 도시가 하드코딩된 곳 (여기만 고친다)
| 위치 | 지금 | 바꿀 것 |
|---|---|---|
| `data/bronze/platform13/`, `data/gold/platform13/` | 도시 묶음 이름이 `platform13` 로 박혀 있다(실제로는 54거점이라 이름부터 어긋나 있다) | **배치 이름을 상수로 뽑는다.** 서울은 `platform13` 유지(호환), 신규는 `goyang` · `paju` |
| `apps/backend/app/data/seoul_pages.py` | 54거점 시드 + 파일명부터 seoul | **파일을 쪼개지 않는다.** `DISTRICTS[*]` 에 `city` 필드를 더하고, 고양·파주는 같은 레지스트리에 이어 붙인다 |
| `data/config/rone_districts.py` | `DISTRICT_RONE` 서울만 | 경기 3매핑 추가 + `SHARED` 표기 |
| `data/collectors/seoul_*.py`, `living_population*.py` | 서울 API 고정 | 신규 `gg_*.py` 를 **형제로** 만든다. 기존 파일은 손대지 않는다 |
| `apps/backend/app/schemas/district.py` | `city` 없음 | `city: str` 추가(서울 기본값) |
| `apps/frontend` SeoulDashboard | 서울 25구 전용 | 도시 선택을 레일이 아니라 **거점 보드의 필터**로 — 화면을 새로 만들지 않는다 |

### 4-C. 신규 파일 (제안)
```
data/config/cities.py              도시 레지스트리 — 시도코드·소스 세트·포털 키 이름
data/collectors/gg_living_move.py  경기데이터드림 유입/유출 생활이동인구
data/collectors/gg_trdar.py        경기도 발달·골목상권 추정매출(분기)
data/collectors/city_events.py     시 단위 행사 — 고양·파주(서울 수집기는 그대로 둔다)
docs/feature-city-expansion.md     이 문서의 후속 — 실행 기록
```

**하지 않을 것: `data/collectors/goyang_*.py` 처럼 도시마다 수집기를 복제하는 것.**
경기 소스는 시군 파라미터를 받는 하나의 수집기로 충분하다. 도시가 늘 때마다 파일이
늘면 서울 수집기가 이미 겪은 분기(서울 API ↔ 전국 API 이중화)를 반복하게 된다.

## 5. 단계별 로드맵 — 통과 조건을 먼저 적는다

| Phase | 하는 일 | 통과 조건 | 선행 |
|---|---|---|---|
| **0. 키·후보 확정** | 경기 포털 3종 키 발급 · 후보 지점별 건물당 점포 비율 프로브 | 키 3종 응답 200 · 후보 지점 비율표 확보 | — |
| **1. Page 최소 성립** | 거점 등록 → 폴리곤·점포·대장 수집 → 공실 산출 → 지도 | 거점별 `coverage.json` **tier1** · R-ONE 앵커 대조 가능 | 건축HUB 쿼터 |
| **2. Platform 정체성** | 카카오·블로그·트렌드 수집 → `program_content_context` 생성 | `/commercial-districts/{id}/platform` 이 200 · archetype 판정 | Phase 1 |
| **3. 수요신호 교체** | 경기 생활이동·추정매출 → `demand` 행 생성 | 시간대·연령·성별 6구간이 서울과 **같은 스키마**로 채워짐 | Phase 0 키 |
| **4. Posting** | R-ONE 경기 매핑 + 공유 표기 → 3-Tier | 회수불가 비율이 서울 대역(0.5~3%) 안 · `rone-shared` 배지 노출 | Phase 1·3 |
| **5. Program** | 시 행사 소스 확인 → 행사·콘텐츠 | 행사 실데이터 or **빈 상태 명시**(시드로 채우지 않는다) | Phase 2 |
| **6. ML 재학습** | LSTM/GNN 에 경기 거점 포함 여부 판단 | **판단을 먼저 쓴다** — pooled 에 넣을지, 도시별로 나눌지 | Phase 4 |

### 쿼터 견적 (Phase 1 의 유일한 실질 병목)
서울 54거점 대장 수집은 08-17 완주까지 **날짜를 나눠 조금씩** 모았고, 08-20 에는
쿼터 672콜을 태워 22동을 얻은 사고도 있었다(미시도 필터 부재). 고양·파주 6거점이면
서울 54거점의 **약 1/9** 규모이나, 정확한 견적은 Phase 0 의 건물 수 프로브 뒤에 낸다.
`scripts/quota_preflight.py` 를 그대로 쓴다 — 도시 가정이 없다.

## 6. 거점 후보 (Phase 0 에서 확정)

프로브 결과와 R-ONE 표본을 겹쳐 본 1차 후보다. **확정이 아니다** — §3-B 비율을 재고 정한다.
