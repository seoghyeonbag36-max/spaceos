**3D 트윈 층 실배치 — 연결 완료 (2026-08-17).**
트윈이 "몇 층이 비었나"를 **실측 층 번호**로 그린다. 종전에는 점유율만큼 **아래부터 채우는
근사**여서, 3층이 비고 1층이 찬 건물도 1층부터 찬 것으로 그려졌다.

원인은 데이터 부재가 아니라 **파이프라인이 층 번호를 버린 것**이었다. `build_page_master._aggregate`
는 상업층 집합(`capacity_floors`)과 점포 확인 층(`store_flr_nos ∪ 인허가 층`)을 이미 계산해
놓고 **개수만**(`active_floors_lo/hi`) 남겼다. 층 번호를 산출물에 실어 프론트로 흘린다.

| 새 property | 뜻 |
|---|---|
| `com_floors` | 상업 용도 층 번호 — 공실률의 **분모** |
| `occ_floors` | 점포(상가정보 flrNo)·인허가로 **확인된** 영업 층 — 분자의 하한 |
| `unknown_n` | 층 미상 점포로 빈 상업층에 배정된 층 수(상한 − 하한) |

트윈은 층을 4색으로 구분한다: 영업 확인(녹) · 층 미상 배정(황) · 공실(상태색) ·
**비상업 층(회, 좁게)**. 마지막이 특히 중요하다 — 종전 트윈은 주거·업무 층까지 상가인 양
그렸다. `com=[1,4,5]` 인 건물이면 2·3층은 분모 밖이라는 게 화면에 드러난다.

- 층 미상 점포를 앉히는 규칙은 파이프라인과 **동일**하게 맞췄다(빈 상업층에 낮은 층부터).
  어긋나면 트윈의 녹색 층 수와 카드의 `vacancy_rate` 가 서로 안 맞는다.
- 층 근거가 없는 건물은 **종전 근사로 폴백**하되, 캡션에 "아래부터 채운 근사"라고 밝힌다.
- 배선: `_aggregate` → gold 마스터 properties → `services/building_vacancy` 는 gold 를 그대로
  통과시키므로 **백엔드 변경 없음** → `MapShell` · `PageDashboard` → `BuildingTwin`.
- 재산출 영향: 54거점 coverage.json 이 전부 `built_at` 한 줄만 바뀌었다 — **수치 드리프트 0**.
  마스터 합계 29.7 → 30.7MB (+3.4%).

#### 다음 단계 — 아래 생활인구 설계는 여전히 유효하다 (보완재다)

TRDAR 과 생활인구는 어느 하나가 낫다기보다 **축이 반대**다:

| | TRDAR(오늘 배선) | 생활인구(계획) |
|---|---|---|
| 시간 | 6구간 | **00~23시 실측** |
| 공간 | 상권(거점당 1~9) | 행정동 — **거점보다 넓다** |

즉 시간은 생활인구가, 공간은 TRDAR 이 낫다. 합치는 것이 맞다 — 생활인구로 **시간
곡선**을 얻고 TRDAR 상권으로 **공간 가중**을 주면 두 축 모두 실측이 된다.

**정해진 설계**(생활인구) — 두 축의 출처를 나눠 적는다:

| 축 | 소스 | 성격 |
|---|---|---|
| 시간 | 서울 생활인구 행정동×00~23시 | **실측** |
| 공간 | 건물 좌표 × 상업면적 가중(`page_building_master.geojson`) | **실측 앵커 + 분포는 모델** |

⚠ 행정동은 거점보다 넓다. 그래서 이 배선으로도 **거점 내 공간 분포는 여전히 모델**이다
— 화면 라벨을 "생활인구 실측 격자"라고 적으면 안 된다. 50m 격자 실측은 REST 가 아니라

(`ESSENTIAL_PARAMETER_ERROR` 로 막힌 §0-E)를 기다릴 필요가 없어질 수 있다.
→ 수집 후 업태별 SITEAREA 중앙값을 A 후보로 대조할 것.

#### 생활이동 파이프라인 골격

「수도권 생활이동」(서울시×KT, OA-22300 계열)은 **도착시간(0~23) · 출발/도착 행정동 ·
성별 · 나이 · 이동유형(출근·등교·쇼핑·관광·병원·귀가·기타) · 평균 이동시간 · 이동인구**를
준다. 행안부 「지역별 인구이동 현황」과는 다른 물건이다 — 그쪽은 주민등록 전입신고라
**월 단위 거주지 이전**이고 시간대 축이 없어 상권 방문을 못 센다.

```
data/pipelines/build_hub_adong.py       거점 ↔ 행정동 + 상업연면적 가중 (카카오 coord2regioncode)
data/collectors/living_migration.py     ZIP/CSV 스트리밍 → 거점 도착 행정동만 집계 → bronze
data/pipelines/build_page_migration.py  bronze → gold/platform_page_migration.json
```

설계에서 갈린 세 지점:

1. **파일이지 REST 가 아니다.** `/F/` 데이터셋이고 일별 ZIP 이다. 행정동 OD × 24시간 ×
   성 × 연령이라 하루치도 수백만 행 — 원본을 bronze 에 쌓지 않고 **스트리밍으로 읽으며
   즉시 접는다**(`build_building_attrs` 가 85MB 대장을 행 단위로 접는 것과 같은 이유).
   다운로드는 포털 로그인 뒤라 자동화하지 않고, 내려받은 디렉터리를 인자로 받는다.
2. **행정동↔거점을 좌표로 잇는다.** `stores_raw.lnoAdr` 에서 나오는 것은 법정동인데
   생활이동은 행정동이고 둘은 1:1 이 아니다. 변환표를 들이면 그 표가 낡으므로 건물
   좌표를 카카오 coord2regioncode 에 넣어 직접 받는다(약 100m 격자로 뭉쳐 호출 절약).
   한 거점이 행정동 여럿에 걸리므로 **상업 연면적(`com_area_flr`) 가중**을 함께 낸다 —
   08-23 분모 정정이 반영된 값을 그대로 탄다.
3. **컬럼명을 고정하지 않는다.** 포털 배포분마다 헤더 표기가 흔들려, 정규화 후 부분일치로
   매핑하고 하나라도 못 찾으면 **실제 헤더를 찍고 멈춘다.** 조용히 기본값을 쓰면 근거 없는
   숫자가 gold 까지 간다. 이동인구가 `*`(KT 비식별)인 행도 0 이 아니라 `masked_rows` 로
   따로 센다.

산출물은 `build_page_footfall`(체류·밀도)과 짝이다 — 그쪽이 "얼마나 있나", 이쪽이
"몇 시에 · 누가 · 어디서 왔나"다. 둘 다 `resolution` 을 응답에 실어 **행정동/상권 집계이지
건물 단위 실측이 아님**을 밝힌다.

```

python -m data.collectors.living_migration <내려받은디렉터리>
```
