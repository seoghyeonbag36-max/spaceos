## 프롬프트 A — 실측과 문안 (필수)

````text
이 저장소(Co.I)의 실측값을 산출해서, 이미 만들어진 구직 서류 4종의 "Co.I 항목"을 채운다.

## 배경
같은 사람이 두 서비스를 만들었다.
- PlaceOS — 오프라인 상권 디지털 트윈 플랫폼 (별도 저장소, 운영 중: https://placeos.web.app)
- Co.I — 창업 코파일럿 AI (이 저장소)

기술지주회사·산학협력단·창업지원단 지원용 서류 4종(이력서·경력기술서·포트폴리오·
인재풀등록프로필)이 이미 있다. 그 문서의 PlaceOS 항목은 저장소 계측 스크립트에서
뽑은 실측값으로 채워져 있고, Co.I 항목만 "[ 채울 것 ]" 으로 비어 있다.
이 작업은 그 빈칸을 PlaceOS 와 같은 기준으로 채우는 것이다.

## 철칙 — 넷 중 하나라도 어기면 이 작업은 실패다
1. 재지 않은 값은 쓰지 않는다. 모르면 "[미측정]" 으로 남긴다. 그럴듯한 추정치를
   써넣는 것이 이 작업에서 가장 나쁜 실패다.
2. 모든 수치에 산출 근거를 병기한다 — 실행한 명령어 또는 파일 경로.
3. 미달·부족한 항목도 그대로 쓴다. 감추지 않는다. PlaceOS 서류는 자사 모델이
   무정보 베이스라인에 7.7%p 미달한다는 사실을 그대로 싣고 있고, 그 정직함이
   이 서류 묶음의 핵심 신뢰 장치다. Co.I 항목만 장점 나열이면 그 장치가 깨진다.
4. 계측기가 없는 목표는 성과로 적지 않는다. 재고 싶은 값에 계측 코드가 없으면
   "[미측정]" 으로 두거나, 계측기를 먼저 만들고 나서 잰다.

## 1단계 — 실측 (실제로 실행하고 출력을 인용할 것)

### 1-1. 규모와 이력
```bash
git ls-files | grep -E '\.(py|ts|tsx|js|jsx)$' | xargs wc -l | tail -1   # 코드 라인 수
git rev-list --count HEAD                                                # 커밋 수
git log --reverse --format=%ad --date=short | head -1                    # 최초 커밋일
git log -1 --format=%ad --date=short                                     # 최종 커밋일
```
⚠ 저장소가 shallow clone 이면 커밋 수가 실제보다 적다. `test -f .git/shallow` 로
확인하고, shallow 면 커밋 수를 쓰지 말 것.

### 1-2. 검증 체계 — 여기가 가장 중요하다
```bash
ls .github/workflows/                       # CI 존재 여부
grep -rho "^def test_\|^    def test_" tests/ test/ **/tests/ 2>/dev/null | wc -l
```
- 테스트 수, CI 워크플로, "통과해야만 배포" 게이트가 있는지 확인한다.
- 없으면 **없다고 쓴다.** 있는 척하지 않는다.
- ⚠ 이 항목이 AI 보조 개발에 대한 의심("생성된 코드를 본인이 검증하는가")에
  답하는 자리다. 숫자가 작아도 정확한 편이 낫다.

### 1-3. 서비스 실체
- 배포 주소가 있는가. README / vercel.json / Dockerfile / cloudbuild / fly.toml 등 확인
- 지금 살아 있는가. 있으면 URL 을 적고, 없으면 "로컬 실행 단계" 라고 쓴다
- 사용 기술 스택을 의존성 파일(requirements.txt / package.json / pyproject.toml)에서
  실제로 읽어 나열한다. 쓰지 않는 라이브러리를 적지 않는다

### 1-4. Co.I 고유 — 무엇을 자동화했는가
코드에서 아래를 직접 세고, 파일 경로를 근거로 남긴다.
- 창업 의사결정 단계를 몇 개로 나눴는가 (입지·업종·가격대·홍보 등)
- 프롬프트 / 체인 / 에이전트 / 툴 정의가 몇 개인가
- 외부 데이터를 쓰는가, 순수 생성인가, 검색 결합인가
- **환각 차단 장치가 있는가** — 생성물의 사실성을 검사하는 코드가 있는지,
  그것을 고정하는 테스트가 있는지. 없으면 없다고 쓴다

### 1-5. 성능 — 계측기가 없으면 만들고 잰다 (철칙 4)
- LLM 응답 시간 p50 / p95 를 재는 코드가 있는가
- 처리한 질의 수를 남기는 로그나 DB 가 있는가
- 둘 다 없으면 둘 중 하나를 고른다:
  (a) 계측 배선을 먼저 추가하고 표본을 모은 뒤 값을 쓴다
  (b) "[미측정]" 으로 남기고, 서류에는 "계측 배선 예정" 이라고만 쓴다
  ⚠ 표본이 적으면 값을 단정하지 말고 n 을 함께 적는다. n=3 짜리 평균은 성과가 아니다

### 1-6. PlaceOS 와의 연결 — 확인하면 가장 강한 소재가 된다
PlaceOS 는 외부 창업 코파일럿을 붙이기 위해 **자기가 계약을 발행**해 두었다.
공급자가 정해지지 않아 기다리기만 하면 영원히 비는 자리라, 방향을 뒤집은 것이다.

- 계약 이름: `spaceos.posting/1`
- 요청: `POST {copilot_url}/simulate`, `Authorization: Bearer {key}`
  ```json
  {"contract": "spaceos.posting/1",
   "district_id": "garosugil",
   "industry_type": "cafe",
   "unit": {"id": "...", "area": 60, "rent": 850, "prem": 3000,
            "floor": "1F", "foot": "고"},
   "units": {"area": "m2", "rent": "manwon_per_month", "prem": "manwon",
             "invest_mn": "million_krw", "month_cost": "manwon_per_month",
             "month_rev": "manwon_per_month"}}
  ```
- 응답: 3-Tier 시나리오
  ```json
  {"contract": "spaceos.posting/1",
   "scenarios": [{"tier": "premium", "invest_mn": 37.0, "month_cost": 1288.0,
                  "month_rev": 4225.0, "basis": "rent+fitout+cogs+labor"}]}
  ```
- 경계: 공급자는 `invest_mn`·`month_cost`·`month_rev`·`basis` 만 준다.
  파생값(`month_net`·`roi_months`·`viable`)과 추천 기준은 PlaceOS 가 계산한다

이 저장소가 이 계약의 **공급자 쪽을 구현하고 있는지** 확인한다.
- 구현돼 있으면 → 서류에 반드시 쓴다. "두 프로젝트가 규격으로 연결된다" 는
  단순 병렬 나열보다 훨씬 강하다
- 구현돼 있지 않으면 → 지금 구현할 가치가 있는지 판단해서 보고한다.
  엔드포인트 하나이고 계약이 확정돼 있어 비용이 작다

## 2단계 — 채울 칸 (정확히 이 필드들이다)

### 문서 1. 이력서 — 주요 프로젝트 표
- 기간: `2026.MM ~ 현재` 형식
- 내용: 2줄. 1줄은 한 줄 정의, 1줄은 핵심 구성

### 문서 2. 경력기술서 3장
- 기간
- 사용 기술 (의존성 파일에서 실제로 읽은 것만)
- 운영 주소 / 저장소
- 문제 정의 — 1~2문장. "창업자가 원래 며칠 걸리던 어떤 판단을 몇 분으로 줄였는가"
- 해결 접근 — 1~2문장. "무엇을 근거로 답하는가. 환각을 무엇으로 막는가"

### 문서 3. 포트폴리오 5장
- 한 줄 정의
- 해결하는 문제
- 기술 구성
- 정량 지표 ← 재지 않았으면 "[미측정]" + 계측 계획
- 링크: Co.I 주소 / 저장소

### 문서 4. 인재풀등록프로필 4장
- 핵심 성과: 3~4줄. 각 줄이 수치를 포함할 것. 이 문서가 1차 메일의
  유일한 첨부라 가장 중요하다

### 공통 문체 규칙
- 한국어. 기술 용어는 영문 병기
- "~했습니다" 체
- 이모지·특수기호 금지 (문서 폰트 subset 에 없으면 빈칸으로 렌더된다).
  쓸 수 있는 기호: `· — - ( ) [ ] % / : ~ →`
- 형용사로 부풀리지 않는다. "혁신적인", "최적화된" 같은 말을 쓰지 않는다.
  수치가 말하게 한다

## 4단계 — 자기검증 (제출 전 반드시)
- [ ] 모든 수치에 산출 근거가 붙어 있는가
- [ ] 근거 없는 수치가 하나라도 남아 있는가 → 있으면 "[미측정]" 으로 되돌린다
- [ ] 부족한 항목을 감추지 않았는가
- [ ] 이모지·특수기호가 섞이지 않았는가
- [ ] 의존성 파일에 없는 기술을 나열하지 않았는가
- [ ] shallow clone 인데 커밋 수를 쓰지 않았는가

작업을 시작하기 전에 1단계 각 항목을 어떤 명령/파일로 확인할지 먼저 말하고,
확인이 끝난 뒤에 문안을 쓴다. 순서를 바꾸지 않는다.
````

````text
## 반드시 지킬 것 — 한글 폰트 임베딩
폰트 이름만 지정하면 뷰어에서 한글이 □ 로 깨진다. 아래 순서를 그대로 따른다.
1. python-docx 로 문서 생성. 모든 run 에 `w:rFonts` 의 ascii/hAnsi/eastAsia/cs 를
   모두 같은 폰트명으로 지정하고, `docDefaults` 의 `rPrDefault` 에도 박는다
2. 문서에 실제로 쓰인 글자만 모아(`<w:t>` 파싱) fontTools 로 subset
3. ECMA-376 Part1 §17.8.1 난독화: fontKey GUID 16바이트를 역순으로 만들어
   폰트 파일 앞 32바이트를 XOR → `.odttf`
4. 배선 4곳: `word/fontTable.xml`(embedRegular/embedBold + fontKey + subsetted="1") ·
   `word/_rels/fontTable.xml.rels` · `[Content_Types].xml` 에 odttf Default ·
   `word/settings.xml` 에 `<w:embedTrueTypeFonts/><w:saveSubsetFonts/>`

## 함정
- 표는 table 의 `columnWidths` 와 모든 cell 의 `width` 를 둘 다 DXA 로 준다
- 표 음영은 `ShadingType.CLEAR`. SOLID 는 검게 렌더된다
- 문단 테두리는 top/bottom 만. 4면 지정은 OOXML 스키마 위반이다
- 이모지를 쓰지 않는다. subset 에 없으면 빈칸이 된다

## 검증 (생략 금지)
- odttf 를 복호화해 sfnt 매직(0x00010000 / OTTO / true)인지 확인
- 문서 고유 글자가 전부 subset 폰트 cmap 에 있는지 확인 → **누락 0자**여야 한다
- 가능하면 PDF 로 변환해 눈으로 본다. 변환기가 없으면 그 사실을 보고한다
````

## 운영 메모

- 프롬프트 A 는 **측정 → 문안** 순서를 강제한다. 이 순서가 뒤집히면 그럴듯한
  문장이 먼저 나오고 수치가 거기 맞춰 발명된다. 이 저장소 묶음에서 가장 경계하는 실패다
- `spaceos.posting/1` 공급자 구현 여부는 A 의 1-6 에서 반드시 확인시킬 것.
  구현돼 있으면 Co.I 항목의 무게가 달라진다
- 1차 메일의 유일한 첨부는 인재풀등록프로필이므로, **문서 4 의 칸이 최우선**이다
