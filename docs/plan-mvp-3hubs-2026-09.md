# 9월 미션 개발 과정 — 3거점 MVP → 66거점 루프 엔지니어링

> 미션: **연남동·신촌·홍대 3곳의 MVP 를 완벽하게 만들고, 이를 바탕으로 66거점을 루프 엔지니어링으로 완성한다.**
> 형제 문서: [plan-design-upgrade-2026-09.md](plan-design-upgrade-2026-09.md) (디자인 고도화 과정)
> §0 의 수치는 2026-09-06 `scripts/chain_status.py` · `scripts/pppp_status.py` 실측이다.

## 0. 미션 재정의 — 실측이 전제를 바꾼다

미션 문장은 "3거점을 만들고 → 66거점으로 넓힌다"를 뜻하는 것처럼 읽힌다.
그런데 **데이터는 이미 66거점이 다 서 있다.** 3거점은 셋 다 9단계 체인을 전부 통과했다.

| | 연남동 | 신촌·이대 | 홍대 |
|---|---|---|---|
| 체인 | **9/9** | **9/9** | **9/9** |
| 점포 / 건물 | 5,969 / 1,862 | 4,659 / 1,492 | 7,758 / 2,109 |
| 대장 실측 | 1,682동 | 1,376동 | 1,927동 |
| 정밀 분모 | 99.1% (잔여 0) | 97.1% (잔여 0) | 99.3% (잔여 0) |
| Page 마스터 | Tier1 · 노출 1,133동 | Tier1 · 노출 1,443동 | Tier1 · 노출 1,325동 |
| 대표 공실률 | 12.5% | 17.2% | 15.0% |
| R-ONE 앵커 | 5.0% (**+7.5%p**) | 11.68% (**+5.52%p**) | 8.1% (**+6.9%p**) |
| 공실 유닛 | 12 (층별 296) | 12 (층별 395) | 12 (층별 559) |
| 서빙 등재 | ✅ | ✅ | ✅ |

그리고 PPPP 게이트 24개가 **네 트랙 모두 100%** 다. 상태 스크립트가 스스로 붙인 경고가 정확하다 —
*"게이트 배선이 끝났다는 뜻이지 제품이 끝났다는 뜻이 아니다."*

### 그래서 이 미션의 실제 뜻

| 겉으로 읽히는 것 | 실제로 해야 하는 것 |
|---|---|
| 3거점 데이터를 완성한다 | ❌ 이미 됐다 |
| **3거점에서 "쓸 수 있는 화면"을 완성한다** | ✅ **여기가 미션이다** |
| 66거점으로 데이터를 넓힌다 | ❌ 이미 66이다 |
| **3거점에서 굳힌 화면 규칙을 66거점에서 안 깨지게 만든다** | ✅ **이게 루프 엔지니어링이다** |

⚠ **"수집 과제로 적기 전에 이미 있는지 먼저 센다"** — 이 저장소가 사흘에 네 번 당한 양식이다.
이번에도 같다. 미션을 수집 계획으로 번역하면 3주를 날린다.

## 1. MVP 통과 조건 — 무엇이 "완벽"인가

게이트 24개는 **배선**을 센다. MVP 는 **사람이 결론에 도달하는지**를 센다. 다른 자다.

### 1-1. 기준 시나리오 (연남동)

> **김민수(34) · 카페 창업 희망 · 예산 1.5억 · 연남동 선호**
> 앱을 처음 열어 **5분 안에** 아래 넷을 얻는다. 도움말·설명 없이.

| # | 트랙 | 얻어야 하는 것 | 데이터 근거 (이미 있다) |
|---|---|---|---|
| ① | **Platform** | 연남동은 어떤 상권인가 — 골목 트렌드 · 주 이용 연령 · 피크 시간 | TRDAR 수요신호(24시간) · 집계구 유동·밀도 · 블로그 키워드 |
| ② | **Page** | 어디가 비었나 — 건물·층 단위 | 노출 1,133동 · 대표공실 12.5% · 층별 공실 유닛 296 |
| ③ | **Posting** | 그 자리 얼마고 몇 개월에 회수되나 | 3-Tier(고급화/가성비/기능중심) · R-ONE 임대료 · 회수기간 |
| ④ | **Program** | 어떻게 알리나 | 온라인(퍼포먼스) / 오프라인(상권활성화) 분리 출력 |

### 1-2. 페르소나 3개 — 셋 다 통과해야 한다

| 페르소나 | 진입 화면 | 이 사람의 결론 |
|---|---|---|
| 소상공인 김민수 | 지도(연남동) | 후보 3자리 + 각각 회수기간 + 홍보안 1장 |
| 프랜차이즈 출점팀 | 거점 탐색(Hub Explorer) | 66거점 중 출점 후보 3곳 + 배제 근거 |
| 지자체 담당자 | 서울 대시보드 | 우리 구 공실 추이 + 활성화 프로그램 후보 |

⚠ 프랜차이즈 페르소나는 화면설계서가 **이미 있다** → [screen-hub-explorer.md](screen-hub-explorer.md).
새로 쓰지 말고 그 문서의 §10 구현 순서를 따른다.

### 1-3. 측정 가능한 통과 조건 (MVP 완료 판정)

```
[C1] 3거점 각각에서 시나리오 ①~④ 를 뒤로가기 없이 완주한다
[C2] 각 화면의 결론 문장이 스크롤 없이 첫 화면에 보인다
[C3] 콘솔 에러 0 · pageerror 0  (거점 3 × 탭 4 = 12조합 전부)
[C4] 지도 초기 렌더 3초 이내 (KPI①)
[C5] 화면에 뜬 모든 수치가 출처를 말한다 (§2 신뢰 규칙)
[C6] 3거점에서 같은 조작이 같은 자리에 있다 (거점별 예외 화면 0)
```

## 2. M2 — 신뢰 확보: 데모가 무너지는 세 자리

**이걸 M3(화면)보다 먼저 한다.** 화면을 다 만든 뒤에 수치 해명을 붙이면 레이아웃을 다시 짠다.

### 2-1. 앵커 격차 +5.5~+7.5%p

우리 대표 공실률이 R-ONE 앵커보다 **일관되게 높다**(3거점 전부 +). 미팅에서 반드시 나온다 —
*"한국부동산원은 5%라는데요?"* 여기서 답을 못 하면 나머지 실측이 통째로 의심받는다.

- **원인 가설**: R-ONE 은 중대형 상가 **표본 조사**, 우리는 대장 기반 **전수**다. 표본에서 빠지는
  소형·이면 건물이 공실률을 끌어올린다 — 그렇다면 격차는 오류가 아니라 **우리 커버리지의 증거**다
- **할 일**: 가설을 실측으로 확정한다 → `/probe-first` 로 `docs/finding-anchor-gap-2026-09.md`.
  건물 규모별로 우리 표본을 잘라 R-ONE 대상 규모만 남겼을 때 격차가 줄어드는지 본다
- **화면 요건**: 공실률 옆에 **"전수 실측 12.5% / 중대형 표본 기준 N%"** 두 수를 같이 그린다.
  ⚠ 앵커 대조 데이터는 66거점 전부 이미 있다(`[자동] R-ONE 앵커 대조 보유 66/66`)

### 2-2. 공실 유닛이 거점당 12개로 보인다

`vacant_units.json` 은 거점당 **12유닛**인데 `vacant_floor_units.json` 은 **296~559**다.
Posting 화면이 12개만 보여주면 *"연남동에 빈 자리가 12개뿐?"* 으로 읽힌다 — 실제로는
층 단위 공실이 296개다.

- **할 일**: 12가 상한(선별)인지 전량인지 확인하고, 화면이 **"층별 공실 296곳 중 조건 적합 12곳"**
  으로 말하게 한다. 숫자를 줄이는 게 아니라 **줄인 이유를 말하는** 문제다

### 2-3. 커버리지 두 눈금이 섞여 있다

`coverage.json` 의 `coverage_pct` 는 연남 41.7 · 신촌 39.0 · 홍대 60.1 인데,
체인의 "정밀 커버리지"는 셋 다 100.0% 다. **다른 것을 재는 두 수**다
(전자는 노출/제외 비율, 후자는 분모 정밀도). 화면이나 자료에 하나만 쓰면 반드시 오해가 난다.

- **할 일**: 어느 수를 화면에 낼지 정하고, 나머지는 화면에서 뺀다. 둘 다 내야 하면 라벨을 다르게 쓴다
- ⚠ 관련 함정 기록: `data/gold/*/coverage.json` 을 세면 **73** 이 나오지만 그건 서빙 거점 수가 아니다
  (서빙 66 + 경기 보류 산출물 7). 서빙 목록의 단일 기준은 `app.services.districts.PAGES`

## 3. M 단계 전체

| 단계 | 내용 | 작업일 | 완료 판정 |
|---|---|---|---|
| **M1** | 시나리오 고정 — 페르소나 3개를 종이에 끝까지 그린다 | 1 | `design/planning/00-idea-map.md` 에 3개 여정 |
| **M2** | 신뢰 확보 — §2 의 세 자리 | 2 | `docs/finding-anchor-gap-2026-09.md` + 화면 요건 3줄 |
| **M3** | 화면 개편 — **디자인 고도화 D5 와 같은 작업이다** | 5~8 | [plan-design-upgrade-2026-09.md](plan-design-upgrade-2026-09.md) §7-1 통과 조건 7개 |
| **M4** | 3거점 동시 검증 | 2 | §1-3 의 C1~C6 을 3거점 전부에서 |
| **M5** | 루프 엔지니어링 — 66거점 회귀 | 2~3 | §4 의 화면 루프가 66거점을 돈다 |
| **M6** | 데모 고정 | 1 | 시나리오 녹화 + 실패 시 폴백 경로 |

⚠ **M3 를 디자인 고도화와 따로 세지 않는다.** 두 문서가 같은 작업을 가리킨다.
따로 계획하면 같은 화면을 두 번 고치게 된다.

### M4 가 특히 중요한 이유

연남동에서만 맞춘 화면은 66거점에서 반드시 깨진다. 3거점이 서로 다른 성격이라 **의도된 대조군**이다:

| | 연남동 | 신촌·이대 | 홍대 |
|---|---|---|---|
| 성격 | 골목 트렌드 | 대학 문화 | 청년 문화 |
| 반경 | 500/700m | **600/800m** | 500/700m |
| 공실률 | 12.5%(최저) | **17.2%(최고)** | 15.0% |
| 점포 밀도 | 3.2/동 | **3.1/동** | 3.7/동 |

→ **신촌은 반경이 다르고 공실이 가장 높다.** 연남 기준으로 잡은 지도 줌·범례 눈금·
카드 개수가 신촌에서 처음 깨진다. 그래서 M4 를 M5 앞에 둔다.

## 4. 루프 엔지니어링 설계

"루프 엔지니어링으로 66거점 완성" — 무엇을 루프로 도는가부터 정한다.

### 4-1. 이미 도는 루프 (데이터) — 새로 만들지 않는다

| 자산 | 하는 일 |
|---|---|
| `scripts/chain_status.py` | 거점별 9단계 통과 여부 + 다음 한 수 |
| `scripts/pppp_status.py` | 4트랙 게이트 24개를 산출물에서 계산 |
| `scripts/run_hub_chain_batch.py` · `resume_hub_chain.py` | 거점 체인 배치·재개 |
| `.claude/skills/loop-engine` | 산출물을 읽고 다음 skill 을 스스로 고르는 루프 |
| `.claude/skills/hub-chain` | 거점 하나를 등록→서빙까지 미는 선형 체인 |

**이 루프는 이미 66거점을 완주했다.** 여기에 더 넣을 게 없다.

### 4-2. 없는 루프 (화면) — 이걸 만든다

66거점을 **화면으로** 돌면서 깨진 곳을 찾는 장치가 없다. 지금 화면 검증은
`/verify` 가 사람 손으로 한 거점씩 여는 방식이다 — 66거점 × 4탭 = 264조합을 손으로 못 돈다.

**제안: `scripts/screen_loop.py`** (신규)

```
입력: 거점 목록 = app.services.districts.PAGES (66)
루프: 거점마다
  1. 백엔드+Vite 를 띄운 상태에서 4탭을 연다
  2. 검사 4종
     [S1] 콘솔 에러 0 · pageerror 0
     [S2] 지도 캔버스 visible + SDK 자식 ≥ 1
     [S3] 필수 요소 존재 — 공실 마커/폴리곤 수 > 0 · 결론 문장 노드 존재
     [S4] 초기 렌더 3초 이내 (KPI①)
  3. 실패한 거점·탭·이유를 기록
출력: reports/screen_loop.json + 실패 거점만 스크린샷
```

**설계 제약 (전례에서 나온 것)**

- ⚠ **`@playwright/test`(Node)를 새로 깔지 않는다.** Python `playwright` 가 2026-07-24 부터 있고
  `/verify` 가 그걸 쓴다. 두 벌을 두면 검증 기준이 갈린다 → [prompt-playwright-e2e.md](prompt-playwright-e2e.md) 상단 만료 경고
- ⚠ **거점 목록을 하드코딩하지 않는다.** 그 문서가 만료된 이유가 slug 13개를 박아 둔 것이다.
  `districts.PAGES` 를 런타임에 읽는다
- ⚠ **셀렉터를 좁게 쓴다.** `.b-name` 은 목록행과 상세패널 **양쪽**에 있어
  `querySelector('.b-name')` 이 목록 첫 행을 집는다. `.b-detail .b-name` 으로 좁힌다(2026-09-06 실측)
- ⚠ 66거점 × 4탭이면 시간이 든다. **무인 실행**이 전제다 → `.claude/skills/autorun`
  (절전 억제 · `PYTHONIOENCODING=utf-8` · 체크포인트 재개)

### 4-3. 루프의 판정 기준을 어디에 둘 것인가

`chain_status.py` 가 데이터 9단계를 세듯, 화면 루프도 **통과/미통과를 세야** 진행률이 된다.
→ M5 완료 시 `pppp_status.py` 에 **화면 게이트**를 한 줄 추가하는 것을 검토한다.

⚠ 다만 지금 게이트 24개 중 **선언 게이트가 8개**다. 상태 스크립트가 스스로 적어 둔 대로
*"선언이 많을수록 이 숫자를 믿을 이유가 줄어든다."* 화면 게이트는 **자동(측정) 게이트로만** 넣는다.
측정할 수 없으면 넣지 않는다 — 선언 9번째를 만들지 않는다.

## 5. 일정 (2주 · 작업일)

```
W1  월  M1 시나리오 고정
    화  M2 앵커 격차 probe
    수  M2 마무리 + D5-0/1 토큰(Tailwind 제거·폰트·타입스케일)
    목  D5-2 여백 토큰 일괄 치환
    금  D5-3 4트랙 색 + AA 대비 검사
W2  월  D5-4 design/components 실투입
    화  D5-5 red-dot 이식 + 줌별 전환      ← 디자이너 피드백 핵심
    수  D5-6 글자 정리(결론 1줄 + 근거 3줄)
    목  D5-7 4P 플로우 + M4 3거점 검증
    금  M5 화면 루프 66거점 (무인 야간 실행) → M6 데모 고정
```

병행: 랜딩(D1~D4·D6)은 **주말·자투리**에 둔다. 앱이 본체다.

## 6. 하지 말 것

1. **미션을 수집 계획으로 번역하기** — 3거점 다 9/9 다. 이미 있는지 먼저 센다
2. **연남동만 맞춰 놓고 66거점으로 넘어가기** — 신촌이 반경·공실률 둘 다 다르다(§3 M4)
3. **`@playwright/test` 신규 설치** — Python playwright 가 이미 있다(§4-2)
4. **거점 slug 하드코딩** — `districts.PAGES` 를 런타임에 읽는다
5. **선언 게이트 추가** — 측정 못 하면 게이트로 만들지 않는다(§4-3)
6. **M3 를 디자인 고도화와 따로 계획하기** — 같은 작업이다(§3)
7. **앵커 격차를 화면에서 숨기기** — 숨기면 미팅 한 번에 무너진다(§2-1)
